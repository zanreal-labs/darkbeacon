# Darkbeacon vs Wanderer: feature-parity audit

Audited 2026-10-12. Both repos were read only, nothing was changed.

**What is compared.** The target is a 1:1 replacement of our deployed Wanderer fork, `/Users/zanreal/Developer/wanderer` `main` at `43611995`. That fork is upstream v1.103.4 plus 99 of our own commits: dangerous and bubbled connections and signatures, labels, Ctrl+Z, standings and sovereignty, NPC kills, "who flies here", Ansiblex bridges, way home and shared homes, the rolling calculator, export/import, mobile, and kill routing. Every feature of the fork counts as parity scope.

The other side is Darkbeacon `main` at `37455ae`, plus its unmerged branches:

- `feat/external-access`: 13 commits ahead and 43 behind; 31 conflicts on a trial merge.
- `feat/import-wanderer`: 4 commits ahead; merges cleanly.
- `perf/scale`: 17 commits ahead; 11 conflicts.
- `wip/panels-start`: 1 commit; stale.
- `feat/system-intel` and `feat/jump-planner`: created but still at `main` with 0 commits.
- `feat/passages`, `feat/bookmark-numbering` and the `ui/*` and `ux/*` branches are already merged.

**How it was checked.** Wanderer behaviour was taken from its code, its 29 news posts (`priv/posts`, the same set as wanderer.ltd/news), CHANGELOG and README. Every Darkbeacon status was confirmed by reading code. Spot checks were re-run by hand: the block semantics, the missing ping producer, and the fact that both new branches are empty.

**Legend**

- **Status:** Done, Partial, In flight (branch), Missing, Replaced (an intended deviation), N/A (hosted billing, which a self-hosted instance does not need).
- **Priority:**
  - **P0** blocks switching a real alliance. Per the owner, this includes all per-system intel shown on nodes and in the system info widget: kills, sovereignty, standings colouring, NPC kills, "who flies here", effect, region, statics facts and Triglavian/shattered.
  - **P1** is used daily and expected.
  - **P1b** is a feature the fork has, so it stays in 1:1 scope at P1, but it is rarely used or cosmetic. It is the last thing to build. (The original "P2 = nice" bucket collapses into P1b, because the owner put every fork feature at P0/P1.)
- **Size:** S is under a day, M is 1–3 days, L is more than 3 days, for one agent.
- **Jump planner** is the one intended deviation. Darkbeacon replaces Wanderer's Dotlan-link jump planner with a full-screen 2D k-space capital planner on `feat/jump-planner`, so those rows are "Replaced", not gaps.

**Corrections to the brief, found in code**

1. `feat/import-wanderer` does not import anomalies 1:1. Its `translate.ts` keeps cosmic signatures only, and folds Wanderer comments and structures into the system notes, because Darkbeacon has neither entity yet.
2. Pings have an event type (`ping.created`/`ping.removed` in `packages/shared/src/events.ts`) and Discord and webhook consumers, but nothing produces them. There is no use case, no route and no UI.
3. Blocking differs, and this is a security gap.
   - In Wanderer, a corporation or alliance block beats every corporation/alliance grant. Only a character grant gets past it.
   - In Darkbeacon, `packages/core/src/authorization.ts` `resolveMapRole` lets any grant beat a corporation or alliance block.

## 5. Maps, access control, admin, audit and map settings

Licensing and billing are N/A for a self-hosted single-alliance instance. Map export/import, API keys, webhooks, Discord, bridges, the Thera toggle and cross-instance sharing are in sections 4 and 6.

**Security divergence, verified in code.** In Wanderer (`lib/wanderer_app/permissions.ex` `check_characters_access`) any matching block, including one on a corporation or alliance, sets the result to blocked; after that only character-level grants count. In Darkbeacon (`packages/core/src/authorization.ts` `resolveMapRole`) only a `decisive` block (character or account) wins; a corporation or alliance block loses to any grant. So "alliance = member, spy corp = blocked" lets the spy corp in after migration.

## 8. Where Darkbeacon is already better

- **Real-time core.** Every change is an event in a durable, hash-chained log. Clients resume by `seq` or get a snapshot. Edits are optimistic and roll back if refused, with a "Saving…" indicator. Wanderer's SSE backfill reaches back only 10 minutes, in memory.
- **Audit and revert.** Each entry has a field-level diff plus who, which character, which channel, which country and which browser. Histories exist per map, system, connection and person. Single changes can be reverted on the server. CSV/JSON export and configurable retention (default: keep everything) are built in. The map-level UI is still missing (section 5).
- **Tracking runs server-side, with the browser closed.** Jump detection is stricter: two location reads within 20 s, and a docked arrival is not a jump. The ESI client honours ETag/Expires, rate limits and the error limit. Auto-mapping and passages are durable and idempotent; the first jump through a new hole is recovered. Sold characters are detected by owner hash. Roles are re-checked every 60 s.
- **Routing is in-process.** There is no external route-builder service. It uses SDE gates plus the chain, with cached jump tables. It adds modes Wanderer lacks: high-sec only, outlaw (staging next to trade hubs) and "for this pilot" (faction police). Exits are computed on the server and drawn under exit nodes as nearest hub, jump count and the kind of space the route crosses. Statics not yet opened are listed. Trade hubs are always available, and personal hubs work across maps.
- **Connection intel on the server.** Wormhole type is resolved from either side's sig or a single fitting static. Remaining mass and time are estimated from passages and from the moment the mass status was marked. The intel says which hull classes fit, sorts by urgency, and accounts for frigate-hole mass regeneration. The web UI does not show it yet.
- **Signature paste is safer.** It runs in one transaction and never downgrades a known sig. Replace mode refuses to delete when the paste was unreadable. The toast reports new, updated, removed and unread lines.
- **Bookmark labels.** Numbering is stable and kept on the server, so everyone sees the same numbers. Templates have variables. Click copies.
- **Readable map.** Every node is the same width. Statics show their destination class ("D845 HS"). Each connection is one two-layer line: time colour outside, mass colour inside, a halo for danger, a size letter. EOL counts down. A legend opens on `L`. The opening view is your last view, else your character, else home. `F` fits, `C` centres. The viewport is kept on the server, so it follows you between devices.
- **Sharing and composite maps.** Map-to-map shares have scopes, consent and revoke. A composite (alliance) map merges several chains with last-writer-wins per field and tombstones. Public read-only links, API keys, OAuth 2.1 and an MCP endpoint are in flight.
- **Access and admin.** Rules can also match Discord guild roles and individual accounts, and admin can come from a Discord role. There is one login, with no separate basic-auth admin. Ownership can be handed over. Sessions can be listed and revoked.
- **Integrations.** Webhooks have a UI, HMAC signing, a durable per-delivery log, a test button and an SSRF guard. A Discord notifier is built in, with no external bot or licence: chain kills read straight from R2Z2, EOL, danger, pings, way home, arrivals, role mentions and quiet hours. There is a plugin SDK with server, web, context-menu and node/edge badge slots. One contract (`routes.ts` plus zod) generates OpenAPI 3.1 and AsyncAPI on the branch.
- **Operations.** One container with SQLite or Postgres. Backups are built in (schedule, retention, restore). OTel and Prometheus, health and ready probes. Multi-replica and an alliance-scale ESI budget are in flight (`perf/scale`).
- **Themes and mobile.** Token themes with WCAG contrast tests. The theme follows the OS and is kept per account. Theme packages can be installed. Phones get a bottom sheet with stops, a tab bar, a PWA and long-press menus.
- **Removing a system hides it and keeps its intel.** Signatures, notes and labels come back when the system does. Wanderer drops sigs after 14 days and loses them on deletion.
