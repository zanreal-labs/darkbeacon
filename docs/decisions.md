# Decisions

Choices made where `docs/SPEC.md` is silent. One line each; newest at the bottom.

- Toolchain pins: Node 24, pnpm 10.34 (`packageManager`), TypeScript 6.0 (typescript-eslint does not support TS 7 yet), NestJS 12, Fastify 5, Kysely 0.29, Vite 8, React 19, React Router 8, TanStack Query 5, Vitest 5, zod 4.
- Workspace packages export TypeScript source under a `source` condition; `tsc -b` (project references) builds `dist/` for production, Vite resolves `source`, Vitest aliases every workspace export to its source (see `vitest.config.ts`).
- Server and packages use NodeNext ESM, so relative imports end in `.js`; the web app uses bundler resolution and extensionless imports.
- Test files are compiled by `tsc -b` too, so they are type-checked; they end up in `dist/` but are never loaded.
- Migrations live in `packages/db/migrations/<module>/NNNN_name.ts` and are named `<module>/NNNN_name`; modules never add foreign keys to another module's tables, so cross-module order does not matter.
- Timestamps and EVE ids use `bigint` columns (Postgres `integer` is 32-bit); the pg driver parses int8 into a JS number. Use `col.*` from `@darkbeacon/db` in migrations.
- `Database` (from `@darkbeacon/db`) is the UnitOfWork: `transaction()` binds a Kysely transaction to AsyncLocalStorage and adapters always query through `database.db()`; nested transactions join the outer one.
- Per-stream `seq` comes from an `event_stream.head_seq` upsert inside the appending transaction; the row lock makes seq order equal commit order, and the head survives pruning.
- Events reach the EventBus through an `afterCommit` hook, so rolled back work never publishes.
- `*.updated` events carry the full DTO and `*.removed` events carry the id, so client reducers are simple upserts/deletes.
- A WS subscribe without `sinceSeq`, with a gap above 1000 events, with pruned history or with a seq ahead of the head gets a snapshot; otherwise the missing events are replayed.
- Snapshots are merged from every provider registered for the stream kind, read in one repeatable-read transaction.
- Subscriptions are authorized on subscribe and re-checked (with a re-resolved actor) after any `access.*` event on that stream or the instance stream, after `access.account_changed` for the connections of that account, and every 60 s for all connections; a signed-in socket whose session no longer resolves is closed (1008).
- The `instance` stream is open to any signed-in account by default; modules may replace that authorizer.
- Use cases throw `DomainError` subclasses (`@darkbeacon/core`); `Result` is for pure functions such as parsers. The HTTP edge maps error codes to 400/401/403/404/409.
- Every non-2xx JSON body is `{ error: { code, message, details? } }` (`ApiErrorBody` in shared).
- Every Nest constructor parameter uses an explicit `@Inject(token)`, so DI never depends on emitted decorator metadata (tests run through Vite).
- REST paths live in `packages/shared/src/routes.ts`; Nest uses the global prefix `api` and controllers declare `nestPath(routes.x.y.path)`.
- `MapAccess` (role of an actor on a map) is a core port implemented by the access module; `requireMapRole` reports maps the actor cannot view as not found so ids do not leak.
- Map role resolution follows Wanderer (`check_characters_access`): a `blocked` rule on a character or account wins; a `blocked` rule on a corporation, alliance or Discord role beats every rule on a group, so only character and account grants get past it (none left means `blocked`); otherwise the highest granting role.
- Instance owners and admins are treated like any account on maps unless the access module decides otherwise.
- Cross-module needs are ports owned by the consumer (`AccessSubjectsSource`, `MapOwnership`, `CharacterTokenSource`) and composed in `apps/server/src/adapters/`.
- Without `SECRET_KEY` the server generates one and keeps it in `DATA_DIR/secret.key`, so a bare `docker run` works.
- `DATABASE_URL` must be a `postgres://` URL when set; anything else is a startup error rather than a silent SQLite fallback.
- `event_log` retention defaults to 30 days, pruned hourly; it becomes an admin setting later.
- Connection vocabulary: time `normal|eol` (< 4 h), mass `fresh|reduced|critical` (> 50 %, 10-50 %, < 10 %), ship size `small|medium|large|xlarge`, bubbled `none|source|target|both`.
- System status values: `unknown, home, friendly, empty, occupied, warning, hostile`; signature groups: `unknown, wormhole, combat, relic, data, gas, ore`.
- `whClass` is the SDE wormhole class id (1-6 C1-C6, 7/8/9 high/low/null, 12 Thera, 13 shattered, 14-18 Drifter, 25 Pochven).
- For the MVP the mapping entities have the same shape as their DTOs; split them when they diverge.
- `plugin-sdk` depends only on core and shared types; plugin ports are narrow facades (`maps`, `universe`, `events`, `notifier`, `clock`).
- The built SPA is served by `@fastify/static` without wildcard plus a catch-all that returns `index.html` (JSON 404 under `/api`); hashed assets are cached for a year.
- The default theme preference is `system`: it follows `prefers-color-scheme` live (and `prefers-contrast: more` picks the contrast theme); the light built-in keeps the id `default`.
- Import boundaries are enforced by a small local ESLint rule (`tools/eslint/boundaries.js`) instead of a plugin.
- Feature modules register themselves with one line each in `apps/server/src/modules/index.ts`.
- The dev compose file has a `dev` service for commands and an `app` service that runs `pnpm dev` on random loopback ports; `DEMO_MODE=true` there.
- Sessions: the `dbk_session` cookie holds a random 32-byte token and the `session` table only its SHA-256; 30 days, sliding (touched at most hourly), httpOnly, SameSite=Lax, Secure when PUBLIC_URL is https; expired rows are pruned hourly.
- OAuth state and the PKCE verifier travel in a sealed `dbk_oauth` cookie (path `/api/auth`, 10 minutes, single use); Discord login sends PKCE S256 too.
- OAuth endpoints are browser navigations: failures redirect to the return path with `?auth_error=<message>`; `returnTo` only accepts same-origin absolute paths.
- Secrets at rest use AES-256-GCM with a per-purpose key derived by HKDF-SHA256 from SECRET_KEY (`eve-tokens`, `discord-tokens`, `oauth-state`).
- Discord tokens are kept to re-read guild roles for the admin guild and every guild used by a Discord-role rule: at login and in the background when older than 5 minutes; a revoked grant clears the roles.
- A Discord admin role only raises `user` to `admin`; it never lowers a stored role.
- Admins and the owner grant or revoke admin on other non-owner accounts (never their own); only the owner transfers ownership and becomes admin.
- One owner per instance is enforced by a partial unique index; racing first logins retry once and become users.
- A character linked to another account can only be claimed when its EVE owner hash changed (the character was sold).
- Linking requests the ESI location, ship and online scopes; corporation and alliance come from ESI affiliation on link and on every token refresh.
- ESI affiliation is `POST https://esi.evetech.net/characters/affiliation` with `X-Compatibility-Date: 2020-01-01`.
- Demo and named local accounts have no Discord id and are found by name; fake characters get a stable id from 3 900 000 000 up, corporation 1000169 by default and no ESI token.
- System and plugin actors are admin on existing maps; API tokens hold their fixed role on their one map.
- One access rule per map and subject (Discord role ids are global, so the guild is not part of the key); a block on a corporation, alliance or Discord role beats every group grant (see map role resolution).
- Instance settings live in `instance_setting` (key -> JSON), by default no admin guild; edited through `GET/PATCH /api/admin/settings`. The default theme is not one of them: the themes module owns it (`PUT /api/admin/themes/default`).
- Map ownership reaches access through `MapOwnershipRegistry.use()` from the mapping module (a constructor dependency would be a DI cycle); until then access sees no maps.
- Outgoing HTTP goes through the `HTTP_FETCH` platform token so tests fake Discord, EVE SSO and ESI at the network edge.
- The signed-in account is served at `/api/accounts/me` as `routes.ts` defines it.
- Removing a system hides it (`visible: false`): attributes and signatures stay, its connections are deleted, clients get `system.removed`; adding it again (or `PATCH visible: true`) restores it and publishes `system.added` plus `signature.added` for the kept signatures.
- Hidden systems are unreachable for every command (404) and are left out of snapshots; nothing is published about them, signature unlinks in a hidden system happen silently.
- Locked systems cannot be moved or hidden unless the same request unlocks them; any member may lock or unlock. A batch move is all or nothing.
- Adding a system or connection that already exists returns it unchanged without an event, so auto-mapping can call it blindly; connections are unique per unordered system pair.
- A system added without a position is placed 280 px right of the right-most visible system (superseded below: `SYSTEM_PLACEMENT`, 360 px).
- New connections: type `gate` when the SDE has a stargate between the systems, else `wormhole`; ship size `small` if a side is a shattered frigate system (class 13), `medium` if a side is C1, `large` for other wormholes, `xlarge` for gates and bridges. `eolAt` is stamped when first marked EOL and cleared on `normal`.
- Linking a signature to a connection requires the connection to touch the signature's system and sets its group to `wormhole`; removing a connection unlinks its signatures.
- Probe scanner paste: only `Cosmic Signature` rows become signatures, anomalies are ignored silently, other lines are reported as skipped; a paste never downgrades a known group or name, wormhole type names ("Unstable Wormhole") are not stored, and `replace` removes nothing when no row was understood. Languages are entries in `SCANNER_LANGUAGES` (EN only for now).
- Map slugs come from the name (`home-chain`, then `home-chain-2`...); an explicit slug that is taken is a conflict. New maps default to the `wormhole` scope.
- Setting labels strips removed label ids from systems (published as `system.updated`); label ids and names are unique per map.
- Event catalogue gains `map.created` (first event of a map stream, carries the MapDto) and `map.removed` (`{ id }`) so plugins, webhooks and other modules can follow the map lifecycle.
- Deleting a map cascades to its systems, connections and signatures through foreign keys inside the mapping tables.
- The universe catalogue is loaded once at startup from `DATA_DIR/universe.json` when an operator puts one there, else from the dataset committed in `packages/sde/data/`.
- The universe dataset is built from CCP's JSON Lines SDE zip (`pnpm --filter @darkbeacon/sde universe`) and committed as `packages/sde/data/universe.json` (~1.2 MB): known space (30xxxxxx) and wormhole space (31xxxxxx) only, wormhole class inherited system -> constellation -> region, falling back to 7/8/9 by security (>= 0.45 high, > 0 low) for the few systems without one.
- The SDE zip is read with a small built-in reader (stored/deflate, no zip64) instead of a dependency.
- The `UNIVERSE_CATALOG` token is provided by a global `UniverseModule`; the catalog is the SDE dataset in memory. Search: case-insensitive prefix matches (alphabetical) first, then substring matches.
- Tracking ports owned by tracking: `AutoMapTarget` (implemented with mapping, token `AUTO_MAP_TARGET`) and `UniverseLookup` (satisfied by the catalog); `CharacterTokenSource` (token `CHARACTER_TOKENS`) is identity's `CharacterService`, which already refreshes EVE tokens once per character at a time.
- `EsiGateway` never throws: it answers `{ ok: false, retryAt }` when ESI must not be asked (bucket nearly empty, error limit, 420/429/Retry-After, 5xx/network backoff 5 s doubling to 5 min, 401/403 retried after 5 min) and the poller simply waits until then.
- ESI rate-limit buckets are per route group and character (`X-Ratelimit-*`); below 10 % remaining a bucket rests for a tenth of its window. The global error limit stops all calls with 10 errors left. `X-Compatibility-Date` is pinned to 2026-08-18.
- The poller ticks every second; location and ship are polled only while the character is online (or not known to be offline), every 5 s or later if `Expires` says so; online every 60 s. It does not run when `NODE_ENV=test`.
- A location change is a `character.jumped` only when the previous location was observed less than 20 s earlier (in this process) and the character did not arrive docked (clone jump / pod respawn); otherwise only `character.moved`.
- Auto-mapping maps a jump when either end is in one of the map's scopes, as a gate when the SDE has a stargate between the two systems, otherwise a wormhole (jump bridges and jump drives also count as wormholes for now). It runs only while the owner still has member rights on the map, and jumps of one map are recorded one at a time.
- New events `character.tracked` (full presence) and `character.untracked` ({characterId}) announce tracking changes, so clients upsert/remove like other entities.
- Presence (location, ship, online) is stored once per character and shared by every map that tracks it; tracking a character requires member rights and the character being linked to the caller's account.
- Plugin install sources: `catalog:<folder>` (first-party packages in `plugins/`, shipped in the image), an npm name with an optional exact version or dist-tag (no ranges; fetched from registry.npmjs.org and checked against its sha512 integrity), or a raw `.tgz` body (`application/gzip`, 20 MB max) on the upload routes.
- Packages are unpacked into `DATA_DIR/plugins/.staging` and validated there; only files and folders are unpacked (no links), 100 MB max; a plugin then moves to `DATA_DIR/plugins/<id>`.
- A fresh plugin install starts disabled so the admin reviews its ports and events first; an upgrade keeps enablement and settings and clears the failure record.
- Plugin entries must be self-contained ES modules (no runtime imports): `DATA_DIR/plugins` has no node_modules. First-party plugins import the SDK as types only.
- A new plugin version is reloaded in place (old one disposed, new module imported with the revision in its URL) instead of restarting the process; the old module stays in memory until the next restart.
- A plugin is disabled after 5 failures in a row (event handlers, HTTP routes, provided notifiers; a success resets the count) or at once when loading or `register()` fails (30 s limit).
- `ctx.on()` throws for event types the manifest does not declare; map events reach a plugin only from maps it is not switched off on, and so do notifications for its provided notifiers.
- Per-map enablement is a list of maps a plugin is switched off on; both switches are instance-admin actions (`PUT /api/admin/plugins/:id/enabled` with an optional `mapId`).
- Plugin settings: instance values validated against the manifest's JSON Schema (via zod `fromJSONSchema`, defaults applied); per-map overrides are stored separately and validated merged over the instance values.
- New plugin port `db` (the instance database through a Kysely handle) for plugins with migrations; it is a trusted port (native plugins run in the server process anyway, so a table-prefix wrapper would only look like a boundary) and the admin panel warns before enabling a plugin that asks for it; a manifest with `migrations` must declare `db`; plugin migrations are recorded as `<id>/<file>` in `plugin_migration` and kept on uninstall, as are the plugin's tables.
- Plugin HTTP routes under `/api/plugins/<id>/...` are open to anonymous callers (`accountId: null`); a route with a `:mapId` parameter gets the caller's `mapRole` and is not reached on maps the plugin is switched off on; `/api/plugins/<id>/assets/<file>` (files next to the web entry, signed-in accounts only) is reserved.
- Plugins read maps through the realtime snapshot providers (`map` kind), so the mapping module needs no extra wiring; universe data comes from `PluginPortProviders.universe`, which the mapping module sets.
- Core commands for plugins live in `PluginCommandRegistry` (global); the plugins module registers `notify`, other modules may add theirs. Plugins may provide only a `notifier`.
- The web plugin API carries the host's React (`api.react`: createElement, useState, useEffect) so web bundles need no React import.
- Plugin admin changes publish `plugin.updated` (full PluginDto) and `plugin.removed` on the instance stream.
- Themes live in the plugins module: theme packages (`darkbeacon-theme.json`) are stored in the `theme` table, no files kept; choices are rows in `theme_choice` keyed `instance` or `account:<id>`. A map default theme is left for later.
- `GET /api/themes` is public (the sign-in page is themed too) and returns every theme with all tokens resolved over its base.
- Webhook bodies are the event envelope JSON; signed as `x-darkbeacon-signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<body>">` with `x-darkbeacon-timestamp` (epoch ms), plus `x-darkbeacon-event` and `x-darkbeacon-delivery`.
- Webhook retries after 10 s, 1 min, 5 min, 30 min and 2 h (6 attempts); each delivery is one row updated per attempt; finished deliveries are pruned after 30 days. A delivery's first `nextAttemptAt` is a lease, so a crash mid-send is retried.
- Webhook secrets (`whsec_<64 hex>`) are shown once and stored AES-256-GCM sealed with a key derived (HKDF) from SECRET_KEY; webhook URLs must be http(s), redirects are not followed and response bodies are never shown.
- Webhook config changes are not events (secrets must not reach the stream); only map admins see them.
- Accounts get an optional `mainCharacterId` and `PUT /api/accounts/me/main-character` (additive contract; the web app shows it on the account page).
- The web app reads the caller's map role from `GET /api/maps` (MapDto has no role); the UI hides what the role cannot do, the server still decides.
- Map permissions in the UI: member edits systems, connections and signatures; manager also locks systems and edits labels; admin also edits map settings and access rules.
- Locked systems cannot be dragged or removed; hidden systems stay on the canvas, dimmed with a dashed border, so they can be shown again.
- Optimistic changes stay as an overlay until the request succeeded and the matching event arrived (or 5 s after success); a rejected request drops the overlay (rollback) and shows the server's message.
- When the map snapshot lacks signatures or characters, the web app loads them over REST; presence is polled every 30 s because newly tracked characters only reach the stream with the next snapshot.
- Connections are straight lines between node borders; node handles only start new connections. EOL is dashed with a thin core in the EOL colour, the stroke colour is the type (gate, bridge) or else the mass left.
- New systems from the search land next to the selected system (or the middle of the visible canvas) and move down until they cover nothing.
- No keyboard delete on the canvas for now; removing goes through the context menu.
- System notes are shown as plain text; markdown rendering comes later.
- Label colours are user data and applied inline; every other colour comes from theme tokens.
- The web app reopens its WebSocket when the signed-in account changes, since the socket authenticates with the cookie at connect time.
- The login page passes its `next` path as `returnTo` to `/api/auth/discord/login`; linking a character returns to `/account`. Both pages show `?auth_error=` messages.
- Plugin web modules get the host React as `api.react` (and on `globalThis.darkbeacon.react`) and must not bundle their own; a crashing slot component renders nothing, and components of a plugin switched off on a map are hidden there.
- `vite --mode mock` (`dev:mock`) runs the SPA against an in-memory API that patches fetch and WebSocket in the page (MSW interceptors, no service worker); production builds drop it.
- Web component tests opt into jsdom per file (`// @vitest-environment jsdom`), so the root Vitest config stays as it is.
- Feature modules depend on each other's real services; the stand-ins they had for missing modules (owner-only or deny-all map access, idle tracking) are gone and live only in test helpers.
- Mapping installs its `MapOwnership` into access's `MapOwnershipRegistry` in `onModuleInit`; access registers the only `map` stream authorizer.
- One universe module serves `/api/universe/*` and the `UNIVERSE_CATALOG` port; mapping, tracking and the plugins' `universe` port all read it.
- Auto-mapping records a jump as the character's owner: it adds (or restores) the missing system 280 px right of the other one, moving down (120 px steps; superseded below: `SYSTEM_PLACEMENT`, 360 px and 150 px steps) until it covers no system, then adds the connection; existing items are left as they are.
- An account's main character is stored on the account (`main_character_id`, `PUT /api/accounts/me/main-character`, own characters only); a main character that was unlinked reads as none.
- The theme choice is stored on the server per account; the browser keeps a copy to avoid a flash before `/api/themes` answers. Order: the account's choice, the browser's copy, the instance default.
- Installed plugins start disabled; the admin enables them in the Plugins tab, where the server's catalogue can be installed with one click.
- `.claude/` (local agent worktrees) is ignored by git, Docker, ESLint and Prettier.
- `/ws` accepts a browser only from the public origin or the host the request was sent to (reverse proxy, dev server); clients without an Origin header are allowed. Frames are capped at 64 KiB and a connection follows at most 50 streams.
- Connections carry `pair_low`/`pair_high` (min/max system id) under a unique index per map; an insert that loses a race inserts nothing and the use case returns the winner. Migration `mapping/0002` keeps the oldest of any existing duplicates.
- Webhooks refuse loopback, private, link-local, CGNAT, multicast and reserved addresses (IPv4 and IPv6, including IPv4-mapped, NAT64, 6to4 and Teredo); the check runs in the DNS lookup of the connection itself, one connection per delivery, so DNS rebinding cannot slip past it. The admin setting `webhooksToPrivateNetworks` lifts it.
- Durable consumers read `event_log` with a cursor per consumer and stream (`event_consumer_offset`); the bus only wakes them (plus a 5 s poll). A handler runs in the transaction that moves the cursor and may return work for after the commit; a new consumer starts at the current heads, and an event a consumer fails on five times is skipped with an error. Webhook queueing and auto-mapping run this way; plugin `ctx.on` handlers stay live-only.
- `map.removed` is followed by durable consumers in access (rules), notifications (webhooks and their delivery logs; the deletion itself is not delivered), tracking (tracked characters) and plugins (per-map switches and settings, published as `plugin.updated`). The map's `event_log` rows age out with retention; its `event_stream` head row stays so a seq is never reused.
- Identity publishes `character.unlinked` ({characterId}) when a character is unlinked or claimed after a sale, and `access.account_changed` ({accountId}) when an account's characters, corporation/alliance (seen on token refresh) or Discord roles change, or its sessions end; both go on the instance stream. Token refreshes write only token validity and affiliation, and only while the character still belongs to the account they were read for.
- The poller polls a character only for the account recorded in `tracked_character` while that account owns it and holds member on the map (rechecked every 60 s and after any `access.*` event); otherwise the entry is untracked with `character.untracked`. Tracking follows `character.unlinked` durably and drops stale presence. Untracking an own character needs no map role.
- `DEMO_MODE=true` replaces the dev sign-in form: `POST /api/auth/demo` signs in the shared "Demo pilot" account (owner on a fresh instance) with two fake characters, the first as main, and the web app calls it by itself when `/api/accounts/me` answers unauthenticated and `/api/auth/providers` says `demo`. `DEV_LOGIN`/`ALLOW_DEV_LOGIN` stay as deprecated aliases (warned about at startup); `POST /api/auth/dev` (named accounts) stays for scripts and tests, in demo mode only.
- The demo map ("Demo chain") is seeded by `apps/server/src/modules/demo` through the mapping use cases as the demo account, whenever that account can see no map (one seeding at a time per process). Systems, statics and wormhole types are real game data (anoik.is static data): home J014348 (C3, D845 + U210), J130256 (C2, O477 into home), J130026 (C5, D364), J121158 (C1, N110), Nourvukaiken, Tama, Amamake, EC-P8R.
- After an explicit sign-out in demo mode the browser remembers it for the tab session (`sessionStorage`), so the sign-in page shows with an "Explore the demo" button instead of signing straight back in.
- The web app reopens its WebSocket after the demo sign-in, after "Explore the demo" and after signing out, because the socket authenticates with the cookie it had at connect time.
- Built-in light and dark themes are generated from one `[light, dark]` palette in theme-sdk. Subtle and derived colours (`color-accent-subtle`, `color-*-subtle`) are `color-mix()` over other tokens, so theme packages that change a base colour get matching tints.
- New tokens: `color-bg-subtle`, `color-surface-hover`, `color-surface-active`, `color-border-strong`, `color-text-subtle`, `color-accent-hover`, `color-accent-subtle`, `color-accent-text`, `color-{danger,warning,success}-subtle`, `color-overlay`, `brand-discord*`, `font-size-{xs,large,title}`, `space-5/6`, `radius-small/large`, `control-height-small`, `shadow-{small,medium,large}`, `motion-{fast,normal,easing}`; token groups `brand`, `elevation`, `motion`. The base font size is 13 px and `space-4` is 16 px (4 px grid).
- `system` is a valid theme id for an account's choice and the instance default (`ThemeAdmin` treats it like a built-in); new instances default to it. The browser's copy of the choice moved to `localStorage['dbk-theme-preference']` so an old copy of a picked light theme does not override the new default.
- The design system lives in `apps/web/src/ui` (one barrel, `../ui`): unstyled Radix primitives (`radix-ui`) for menus, dialogs, select, tabs, tooltips, toasts, checkbox and switch, styled with CSS modules over theme tokens; icons from `lucide-react`; Inter and JetBrains Mono bundled from `@fontsource-variable`. Screens import from `src/ui`, never from Radix directly. Every screen now uses it; the global `.btn`/`.input`/`.field` classes stay only for plugin web components, which cannot import `src/ui`.
- The app shell (`apps/web/src/shell`): `/login` stands alone; every other route renders inside `AuthGate` (session, demo sign-in, redirect to `/login?next=`) and `AppShell` (left rail with Maps and Admin, top bar with breadcrumb, demo badge, live status, theme menu and account menu; a bottom tab bar below 768 px). Pages name themselves in the breadcrumb with `useBreadcrumbs()`.
- Admin and map settings keep their open tab in `?tab=` (`useTabParam`), so a tab can be linked and survives a reload. Map settings tabs: General (with the delete zone), Labels, Access, Webhooks; admin tabs: Instance, People, Plugins, Themes. (Map settings superseded below: a dialog over the map, `?settings=`.)
- Map webhooks are managed in the web app (list, add with event groups such as `system.*`, on/off, test, recent deliveries, delete); the signing secret is shown once after creation.
- The map dock is a 360 px sidebar flush with the right edge when open and a floating tab strip when closed; on phones it is a bottom tab bar with a sheet above it, and the app's own tab bar is hidden on the map (the top bar's back link and account menu stay).
- On phones the breadcrumb shows only the current page with a back link to its parent.
- On phones fitting the map never zooms out below 0.6, so systems stay legible; people pan to the rest (superseded below: 0.75 on phones, 0.9 elsewhere).
- `/` focuses the system search on the map.
- Numbers that sit next to letters (class labels, security, ages in chips) use Inter's tabular figures; JetBrains Mono is kept for ids (signature ids, slugs, versions, Discord and EVE ids).
- Light palette colours used as text were darkened to reach WCAG AA (4.5:1) on their backgrounds: subtle text, success, warning, danger, high/low security, friendly/occupied status, gate and reduced-mass edges. Edge chips mix their status colour with the text colour for the same reason in both modes.
- Screenshots of every screen (light and dark, 1440x900 and 390x844) live in `docs/screenshots/` and are produced by `tools/screenshots/shoot.mjs`, run inside the Playwright image against a running instance.
- The product is renamed Darkbeacon (formerly Wormwright): packages are `@darkbeacon/*`, CSS custom properties `--dbk-*` (not `--db-*`, which reads as database), browser keys and cookies `dbk-*`/`dbk_*`, manifests `darkbeacon-plugin.json` and `darkbeacon-theme.json`, webhook headers `x-darkbeacon-*` (receivers that checked `x-wormwright-signature` must switch). Backwards-compatibility shims, the only places the old name is left on purpose: the HKDF salt `'wormwright'` in both `SecretBox` adapters (changing it would make every stored token and webhook secret unreadable); `LEGACY_MANIFEST_FILE` (`wormwright-plugin.json`) and `LEGACY_THEME_MANIFEST_FILE` (`wormwright-theme.json`), still read with a deprecation warning (`apps/server/src/plugins/manifest-file.ts`); `globalThis.wormwright`, an alias of `globalThis.darkbeacon` for web plugins built before the rename; the `ww-theme-preference` localStorage key, read once and moved to `dbk-theme-preference`; the `ww_session` cookie, still accepted (never set again, cleared on sign-out) until it lapses with its 30-day Max-Age.
- The web app is a Next.js 16 App Router app (16.4.0) instead of the Vite SPA with React Router; this replaces the Vite, React Router, `@fastify/static` SPA serving and `vite --mode mock` entries above (the in-browser API mock is gone: pages now read the API on the server; demo mode is the way to try the UI). `src/pages` became `src/screens` (Next.js reserves `pages/`); routes live in `src/app`.
- Next.js configuration follows the Cache Components guide (https://nextjs.org/docs/app/getting-started/caching, "Enabling Cache Components"; https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents): `cacheComponents: true` with `partialPrefetching: true` set explicitly, as the guide asks (leaving it unset logs a warning). Partial Prerendering is what Cache Components does by default, so there is no separate PPR flag. Self-hosting follows https://nextjs.org/docs/app/guides/self-hosting and https://nextjs.org/docs/app/api-reference/config/next-config-js/output: `output: 'standalone'` with `outputFileTracingRoot` (and `turbopack.root`) at the monorepo root, `public/` and `.next/static` copied into the standalone folder after the build, `X-Accel-Buffering: no` on every page so proxies in front do not buffer streams ("Streaming and Suspense"). Auth routing uses the `proxy.ts` file convention (https://nextjs.org/docs/app/api-reference/file-conventions/proxy; `middleware` is deprecated in 16).
- Rendering: nothing is cached with `use cache`, because every page's data is per visitor and the API does not run during `next build`. The prerendered static shell of every route is the root document (theme CSS and head script), the app frame (rail, top bar, tab bar, theme menu, connection status) and each page's loading UI; the account menu, admin links, demo badge, maps list, account, admin, map and map settings stream in, each behind its own Suspense boundary. Links that mark the current page and the breadcrumb read the URL, so they sit in Suspense boundaries whose fallback is the same markup without the mark (Next.js suspends `usePathname` on routes with unknown params). `next build` lists every route as ◐ (Partial Prerender) except `/_not-found` and `/healthz` (○ static).
- Server components read the API through `src/server/api.ts`: `GET` on `INTERNAL_API_URL` (set by the API server when it starts the web server; `http://127.0.0.1:3000` by default) with the visitor's cookies, answers checked with the route's zod schema from `@darkbeacon/shared`, `ApiError` on failure, deduplicated per request with React `cache`. Their data reaches client components as TanStack Query cache entries (`dehydrate` + `HydrationBoundary`), so the existing hooks start with it and refetch, mutate and roll back as before.
- Every `HydrationBoundary` carries all the queries the client components inside it read on their first render. A query another boundary fills later would already exist (pending) in the browser, `HydrationBoundary` then defers it to an effect, and the first client render no longer matches the server (React error 418).
- New route `GET /api/streams/:stream/snapshot` (`StreamSnapshotDto`: `{ stream, seq, data }`) answers what a WebSocket subscribe without `sinceSeq` would send, with the same authorizer (401 anonymous, 404 for streams the caller cannot follow, so ids do not leak). The map page renders from it, and the browser subscribes with `sinceSeq: seq`, so it only replays what happened after the snapshot. `RealtimeClient.subscribe` and `useStream` take that seq; `useMapStore` takes the snapshot.
- The map canvas and dock are a client component loaded with `next/dynamic` and `ssr: false` (React Flow measures the window); until its code arrived the page shows the same "Loading map…" state as the static shell. The server also reads the universe data of every system on the map, so names and classes are there on the first paint.
- Demo sign-in happens in `proxy.ts`: a page visit without a session cookie calls `POST /api/auth/demo` internally and continues with the new cookie on the request (and `Set-Cookie` on the response), so the first HTML is the signed-in app; without demo mode (404, remembered for a minute) it redirects to `/login?next=`. The proxy only looks at cookies; a session the API no longer knows is found where the page reads the account, and the browser goes to `/login?reset=1&next=…`, where the proxy drops the stale cookie and starts over. `/login` with a session cookie goes on to `next`. Redirects use the visitor's address from `x-forwarded-host`/`x-forwarded-proto` (superseded below: relative redirects, forwarded host not trusted; sign-in only for page visits).
- The demo sign-out memory moved from `sessionStorage` to a browser-session cookie `dbk_demo_out=1`, set by `POST /api/auth/logout(-everywhere)` in demo mode and cleared by `POST /api/auth/demo`, because the proxy has to see it. The browser no longer signs in by itself (`useMe` only reads the session).
- Theme without a flash: the head carries every built-in theme as CSS (`systemThemesCss` in theme-sdk: light on `:root`, each theme under `[data-theme]`, and for `<html>` without `data-theme` the dark and high-contrast themes from `prefers-color-scheme` / `prefers-contrast` media queries) and a tiny blocking script (`src/theme/head.ts`) that applies an explicit choice before the body is parsed: the `dbk_theme` cookie first (not httpOnly, not a secret, one year, `SameSite=Lax`), then `localStorage['dbk-theme-preference']`, then the pre-rename key. `system` leaves `<html>` alone, so CSS decides. A theme package applies its CSS saved in `localStorage['dbk-theme-css']`; without it the page stays on system until the theme list loads. After hydration `ThemeProvider` keeps setting `data-theme` to the resolved theme and follows OS changes live, as before; picking a theme writes the cookie and the localStorage copy.
- Global CSS (`styles.css`) now loads before the CSS modules, so a module rule beats a global helper of equal specificity; where a helper must win on a design-system element the module says so (`.bare:global(.mono)` for mono inputs). `IconButton asChild` clones its child (a link) instead of nesting a second Radix `Slot` under the tooltip's, which rendered different markup on the server than in the browser.
- One container, one public port: Nest listens on `PORT` and is the front door. A Fastify `onRequest` hook hands every request outside `/api` to the web server untouched (body streamed, not parsed; `x-forwarded-for/host/proto` added; answers piped back chunk by chunk); upgrades other than `/ws` (the dev server's hot reload) are forwarded too by a router put in front of the gateway's upgrade listener, which would otherwise close them. While the web server does not answer, pages get a small self-refreshing "Darkbeacon is starting" page (503).
- The API server starts the web server itself (`apps/server/src/web/web-server.ts`): `node apps/web/.next/standalone/apps/web/server.js` on a free loopback port chosen by the OS, with `HOSTNAME=127.0.0.1` and `INTERNAL_API_URL`; its output goes to the Nest logger as `Web`; an unexpected exit restarts it after 1 s, doubling to 30 s (reset after a minute up); shutdown stops it (SIGTERM, SIGKILL after 10 s). `WEB_UPSTREAM` makes it proxy to a server someone else runs (development); `WEB_SERVER_ENTRY` overrides the path; without either and without a build only the API is served (tests). These are deployment internals, not settings people set.
- `/api/health` also asks the web server (`GET /healthz`, a static route of the web app): `web: 'ok'` when it answers, `'off'` when this process serves the API only, and a 503 (`unavailable`, a new `ApiErrorCode`) while it does not answer, so the image's `HEALTHCHECK` reflects both processes.
- Development: `docker compose up app` runs `tsc -b`, the API in watch mode with `WEB_UPSTREAM=http://127.0.0.1:3001` and `next dev` on 3001 inside the container; only 3000 is published (on a random loopback port), so pages, `/api` and `/ws` share one address as in production.
- The web app's packages stay `devDependencies`: the standalone build carries its own traced `node_modules` (Next.js, React; workspace packages are bundled), so the image's production install for the API does not pull them in a second time. The standalone folder is owned by `node` in the image, because Next.js writes its runtime cache next to the build.
- Web component tests run without a Next.js router: `apps/web/src/test/next-mocks.tsx` (a Vitest setup file) replaces `next/navigation` with hooks over jsdom's location and `next/link` with a plain anchor.
- `tools/e2e/smoke.mjs` checks a running demo container from the Playwright image: the first HTML for `/` is the prerendered shell (`x-nextjs-prerender`/`x-nextjs-postponed`) with the account and the maps streamed into it after the fallback, the system scheme is right with JavaScript off, a `dbk_theme` cookie applies before `DOMContentLoaded`, a demo visit never sees `/login`, client navigation keeps the document, the map renders and goes live, a change from another browser arrives over the WebSocket, and no page logs a script or hydration error.
- Wormhole facts: `WORMHOLE_TYPES` in `@darkbeacon/shared` maps every wormhole type but K162 to where it leads (`c1`-`c6`, `hs`, `ls`, `ns`, `thera`, `c13`, `pochven`, `drifter`), from https://wiki.eveuniversity.org/Wormhole_Types (Z006 left out: its listed destination is ambiguous); `WORMHOLE_EFFECTS` names the six system effects with a one-line summary from the system effects section of https://wiki.eveuniversity.org/Wormhole_space.
- `UniverseSystemDto` gains `statics` (type codes) and `effect` (or null), additive. The SDE has no usable per-system statics, so they come from `packages/sde/data/wormholes.json` (system id -> `{ statics, effect }`), which an operator can replace with `DATA_DIR/wormholes.json` like `universe.json`. The committed file only lists systems checked by hand (the demo chain's four); filling it for all of J-space is open (a source the project may redistribute is needed; effects could come from the SDE's secondary suns in the builder).

Tokens: `node-min-width` 168 px, `node-padding` 8px 10px, `node-radius` 8 px, `edge-width` 2.5 px. Edge chips are 11 px in the text colour on the raised surface with the strong border, so they read on any line colour in both modes.

When the chain is wider than that, the view centres on the home system (status `home`), else on the middle of the chain. The bottom-left toolbar (design-system buttons, not React Flow's controls) zooms, fits the whole map and fits the selection (both may go below the readable zoom, down to 0.25) and toggles the connection legend (remembered in `localStorage['dbk-map-legend']`). On phones only fit, fit selection and the legend show (pinch zooms).

In the app it is drawn with theme tokens (ring and core in the text colour, beam in the accent with a fade, `tone="mono"` all `currentColor`); the sign-in page sweeps the beam (and a faint light cone behind the tile) every 9 s, still with `prefers-reduced-motion`. Static icons (favicon, PWA and Apple icons, README marks) are generated by `tools/icons/build.mjs` in the Playwright image with the built-in light/dark colours (the favicon switches with `prefers-color-scheme`); a web test fails when their geometry drifts from the component. The PWA manifest is `src/app/manifest.ts` (static `/manifest.webmanifest`, dark background); `icons/` and the manifest are outside the proxy matcher.

- Sign-in redirects stay on the site: `safeNext` resolves `next` like a browser (`new URL` on a fixed origin), keeps it only when the origin is unchanged and the path does not start with `//`, and refuses backslashes and control characters outright; the proxy builds redirects on the request's own URL, which Next.js sends as a relative `Location`. No forwarded header decides where a redirect goes.
- The front door overwrites `x-forwarded-host` with the `Host` the request was sent to (a reverse proxy in front must keep the visitor's Host, as Caddy does and nginx does with `proxy_set_header Host $host`) and passes `x-forwarded-proto` on only as `http` or `https`. The Discord redirect shown on the sign-in page comes from the API (`discordRedirectUrl` in `GET /api/auth/providers`, built from `PUBLIC_URL`), the same URL the API sends to Discord.
- Demo sign-in in the proxy happens only for page visits: a GET of a known route (`/`, `/account`, `/admin`, `/m/<slug>`) that is a document load (`Sec-Fetch-Dest: document`), a client-side navigation (`rsc`, not a prefetch) or, where browsers send no fetch metadata (plain HTTP), an HTML request from a user agent that is not a known crawler or script. Unknown paths go straight to the 404 page (no session, no redirect); `robots.txt`, `sitemap.xml`, `favicon.ico`, `apple-touch-icon*.png` and `/.well-known/` are outside the proxy matcher.
- `serverGet` awaits `connection()` after reading the cookies, so server components that read the API (and stamp TanStack Query entries with `Date.now()`) run at request time only, never during a runtime prefetch.
- The streamed parts of the app shell (account menu, admin links, demo badge) sit in a `SlotBoundary` each (`src/shell/SlotBoundary.tsx`): when the API fails for one, it shows its placeholder instead of the whole document becoming an error page; Next.js navigation errors pass through. `app/global-error.tsx` is the last resort, a whole document in the design system's look with a retry.
- The theme reaches a new browser with the session: `SignInCookies` (platform, a registry like the actor resolvers) lets modules add cookies wherever identity starts a session (Discord callback, demo, named dev login); the themes module adds `dbk_theme` with the account's own choice, or the instance default when the browser has no choice saved. `PUT /api/accounts/me/theme` sets it too. For a theme package the cookie is `<id>|<built-in>` (`themeCookieValue` in theme-sdk), and the head script applies that built-in theme of the package's colour scheme while the package's CSS is not in localStorage yet; `ThemeProvider` leaves a theme it cannot resolve yet as the head script set it until the theme list answered.

The web server keeps static game data it read in a process-wide map (it does not depend on the visitor and only changes with a release or a new `universe.json`, which restarts both servers), so a map page asks for at most one batch of systems it has not seen yet; the map page reads the account, the map and the maps list in parallel, then the snapshot.
- The map dock's tab strip scrolls sideways when plugin widgets make it wider than its room (hidden scrollbar, scroll snap, a vertical mouse wheel scrolls it, a fade on the side with more tabs, the active tab scrolled into view without moving the page); tab titles are cut at 14 characters with the full title as tooltip. The map's top bar keeps clear of the dock's full width whether it is open or closed, and the map page clips overflow (`overflow: clip`), so nothing can scroll it sideways.

- Wormhole types come from the SDE (build 3586130, 2026-10-07): inventory group 988 "Wormhole", dogma attributes as `dogmaAttributes.jsonl` names them: 1381 `wormholeTargetSystemClass`, 1382 `wormholeMaxStableTime`, 1383 `wormholeMaxStableMass`, 1384 `wormholeMassRegeneration`, 1385 `wormholeMaxJumpMass`, 1457 `wormholeTargetDistribution`. `wormholeMaxStableTime` is in minutes although its unit says seconds (1440 = the 24 h of a high-sec static). QA wormholes are left out; codes with several types (C729, J244) take the lowest type id (their attributes match); K162 has no attributes. Target class -1 (region-bound C729) falls back to `WORMHOLE_TYPES`.
- Where the SDE and the EVE University page https://wiki.eveuniversity.org/Wormhole_attributes disagree on max jump masses (the wiki lists 20 000 t, 300 000 t, 1 350 000 t and 1 800 000 t classes; the SDE has 5 000, 62 000, 375 000, 410 000, 1 000 000 and 2 000 000 t), the SDE wins. The wiki's "total mass varies 90-110 %" is kept as a note on estimates only.
- `WORMHOLE_TYPES` (shared) gains the types the SDE has and the table lacked: Z006 (C3, its destination was "ambiguous" before), I078, L687, O546, O753 and R327 (Pochven) and J492 (low-sec). A server test checks every SDE type's target class against the table.
- Wormhole system effects come from the SDE's `mapSecondarySuns.jsonl`: the effect beacon's type name ("Class 3 Wolf Rayet Effects"), not the sun's type, because the beacon applies the effect (they differ in J005926 and J010569). 1038 wormhole systems have an effect.
- Statics per wormhole system: the SDE has none, so they come from the statics table of WormholeSystems (https://github.com/WormholeSystems/WormholeSystems, `database/seeders/data/wormhole_systems.csv`, MIT, Copyright (c) 2025 WormholeSystems), pinned to commit 48c89bf0d11260567146e5b334ba2c27f4205754 in `packages/sde/src/cli.ts`. It covers all 2604 wormhole systems (C1-C6, Thera, the 25 shattered C13 systems, the five Drifter systems). Checked against Pathfinder's `export/csv/system_static.csv` (https://github.com/exodus4d/pathfinder, MIT, last data change 2020): the two agree on 2593 systems; the 11 that differ (Drifter systems, a few C1/C4-C6 changes) follow WormholeSystems as the newer source. Its licence is kept in `packages/sde/data/wormholes.LICENSE` and the README credits. No Wanderer data is used. This supersedes "the committed file only lists systems checked by hand" above; the four demo systems still match their hand check (tested).
- `pnpm --filter @darkbeacon/sde data [--from <zip>] [--statics <csv>]` rebuilds `universe.json` and `wormholes.json` from one SDE download (`universe` stays as an alias). `wormholes.json` now also holds `types`, `hullClasses` and `shipMasses` (hull mass of every ship type, also unpublished ones); an operator's `DATA_DIR/wormholes.json` without them takes them from the committed file.
- Hull classes for "which ships fit" are SDE ship groups (`HULL_CLASS_GROUPS` in the builder): frigate, destroyer, cruiser, battlecruiser, industrial, battleship, industrial command (Orca, Porpoise), freighter, capital. A class fits a wormhole when its heaviest published hull is at most the max jump mass. Supercarriers and titans are left out: "Supercapital ships such as Titans and Supercarriers cannot go through wormholes at all" (https://wiki.eveuniversity.org/Wormholes).
- A wormhole type's connection size follows its max jump mass: up to 5 000 t `small`, 62 000 t `medium`, 410 000 t `large`, above `xlarge`. Linking a signature typed with a known code (not K162) to a connection, or typing a linked signature, sets the connection to that size (`connection.updated`).
- `UniverseCatalog` (mapping's port) gains `wormholeType`, `wormholeTypes`, `hullClasses` and `shipMass`; the static catalog also offers `systems()` and `gateNeighbours()` for routing. New route `GET /api/universe/wormholes` (`WormholeCatalogDto`).
- Passages: a durable consumer (`mapping.passages`) records each `character.jumped` between two systems the map connects as a row of `map_connection_passages` (hull mass from the SDE, null for unknown ships; propulsion modules and plates are not counted) and publishes `connection.passage` with the additive fields `mass`, `from`, `to`, `passageId`. Auto-mapping adds a connection only after the jump that found it, so a `connection.added` also records the `character.jumped` events between the same pair among the 50 events before it. A jump event is recorded once (unique `event_id`); passages go with their connection.
- Connections gain `massStatusAt` (optional in `ConnectionDto`, column `mass_status_at`), stamped whenever the mass status changes. Mass left = (total x 1 for fresh, 0.5 for reduced, 0.1 for critical, the upper bounds of "More than 50 %", "Less than 50 %", "Less than 10 % remaining" on https://wiki.eveuniversity.org/Wormholes) minus the hull mass of passages since `massStatusAt` (all passages while it is null). Holes whose mass regeneration is at least their total mass (frigate holes) never run out.
- Time left: at most the type's lifetime after the map first saw the hole (the connection or one of its signatures, whichever is older), and at most 4 h after it was marked EOL ("Less than 4 hours remaining"); the panel shows the earlier bound as `expiresBy`. Urgency: `critical` below 10 % mass (marked or estimated) or under 1 h left, `warning` for EOL, reduced or under 4 h; gates are always `ok`. The panel list is sorted by urgency, then time left, then mass left, then age.
- A connection's wormhole type: a typed, non-K162 signature on either side, else (no K162 on that side) the one static of a side whose destination is the other side's class, marked `wormholeTypeFrom: 'static'` as a guess; two or more candidates guess nothing.
- New route `GET /api/maps/:mapId/connections/intel` (`ConnectionIntelDto[]`, viewer) and `GET /api/maps/:mapId/connections/:connectionId/passages`.
- Routing is its own module (`packages/modules/routing`, Nest module `RoutingModule`): ports `RoutingUniverse` (the catalog), `ChainSource` (mapping's repositories), `HubRepository`, `PilotDirectory` (identity + ESI), `WaypointGateway`, and `RouteEdgeSource` for extra two-way edges such as Ansiblex jump bridges from a plugin later (`Router.addEdgeSource`). Map connections of type `bridge` are routed as bridges already; `gate` connections add nothing to the stargates.
- Security for routing (https://wiki.eveuniversity.org/System_security): high-sec is true security >= 0.45; displayed security is rounded to one decimal, except that 0.0-0.05 rounds up to 0.1. Wormhole space (C1-C6, Thera, C13, Drifter) counts as neither; Pochven is known space without high-sec.
- Route modes: `shortest` (fewest jumps), `safer` (entering anything but high-sec costs 50 extra, like ESI's default `security_penalty`), `highsec` (known space only in high-sec; the chain's wormhole systems stay usable, or nobody could leave a wormhole), `outlaw` (never enters high-sec; leaving it from the start is fine), `pilot` (fewest jumps avoiding high-sec levels whose faction police attack the pilot). The start is never "entered", the avoid list is never entered. Options: skip EOL, critical and frigate-only (`small`) connections.
- Faction police thresholds (https://wiki.eveuniversity.org/Security_status): attacked in displayed 1.0 at -2.0 or below, 0.9 at -2.5, 0.8 at -3.0, 0.7 at -3.5, 0.6 at -4.0, 0.5 at -4.5; none in low-sec. The pilot's status is given (`securityStatus`) or read for an own character from ESI `GET /characters/{character_id}` (`security_status`, cached an hour). Pilots with the same number of closed levels share cached tables.
- Route tests use jump counts from ESI `POST /route/{origin}/{destination}` with preference `Shorter` (checked 2026-10-12): Jita-Amarr 11, Jita-Dodixie 12, Jita-Rens 15, Jita-Hek 9. High-sec only Jita-Amarr is 34 (an independent breadth-first search agrees); ESI's `Safer` gives 45 because it also weighs security inside high-sec, so it is no reference for this mode.
- Hubs: the trade hubs Jita (30000142), Amarr (30002187), Dodixie (30002659), Rens (30002510) and Hek (30002053); up to 20 map hubs set by managers (`PUT /api/maps/:mapId/hubs`, event `routes.hubs_changed`) and up to 20 personal hubs per account (`PUT /api/accounts/me/hubs`, no event). Where a mode forbids a trade hub (outlaw, pilot) it is replaced by a `staging` hub: the system nearest to it by stargates that the mode allows (low-sec for outlaws, any known space but Pochven for pilots), inside the largest stretch of space the mode can travel by stargate, first by name on a tie.
- Exits (derived, never stored): `connected` exits are known-space systems on the map with a wormhole connection, with jumps to every hub and the nearest; `static` exits are wormhole systems with statics to high, low or null-sec that no wormhole connection of that system to that kind of space uses yet. New routes `GET /api/maps/:mapId/route`, `/exits`, `/hubs`, `/hubs/distances`, `GET /api/accounts/me/hubs`.
- The router keeps the stargate graph once and per map (64 maps, least recently used dropped) the chain overlay and jump tables to hubs per mode (Dijkstra backwards from each hub, built on demand). Any `system.added|removed`, a `system.updated` that shows or hides a system, or `connection.added|updated|removed` drops the map's state; 250 ms later the exits are recomputed (shortest mode, trade and map hubs) and published as `routes.exits_changed` when they changed, and the safer, high-sec and outlaw tables of those hubs are filled in the background. Map snapshots carry `exits` too.
- In-game waypoints: `POST /api/accounts/me/characters/:characterId/waypoint` calls ESI `POST /ui/autopilot/waypoint` with `add_to_beginning`, `clear_other_waypoints` and `destination_id` and scope `esi-ui.write_waypoint.v1`, as the live OpenAPI spec (compatibility date 2026-08-18, https://esi.evetech.net/meta/openapi.json) lists them; `destination` clears other waypoints, `waypoint` appends. Linking now asks for that scope too; characters linked before lack it until linked again, and `CharacterDto.canSetWaypoints` says which have it.
- Audit trail: the event log is the audit trail. Every appended event gets an audit record in `event_log.audit` (JSON): the actor with the account and the character in use and their names as they were then (the account's main character, or the character that jumped for auto-mapping and tracking), the channel (`web`, `api` + token id, `plugin` + plugin id, `system` + process: `auto-mapping`, `tracking`, `identity`, `demo`, `sign-in`, `plugin-loader`, `plugins`), the request origin (country and user agent, HTTP only), the operation and entity, a field-level diff (`{ field: { before, after } }`) and, for removals, the removed snapshot. The envelope that clients, webhooks and plugins see is unchanged; origins are shown to map admins and instance admins only. The audit module is `packages/modules/audit` (`@darkbeacon/audit`).
- Use cases pass the state before a change as `NewEvent.before` (additive, never published). The audit catalogue (`AUDIT_CATALOGUE`, a `Record` over every event type, so a new type does not compile without an entry) says per type whether it is a create, update, delete or activity, which entity it is about, what it touches (`event_ref` rows: `system:`, `connection:`, `signature:`, `account:`, `character:`, `map:` refs for per-thing and per-person histories) and which fields are bookkeeping. An update without a known before is recorded as a create. A catalogue test builds a record from a sample of every type and fails when one lacks an actor or a diff/snapshot; the HTTP test checks every entry of a real session.
- Audit facts travel in an `AuditScope` (core port; AsyncLocalStorage in the server): a global interceptor opens one per HTTP request (channel and origin), auto-mapping adds its channel and the jumping character, demo seeding runs as `system:demo`, a revert adds `revertOf`. The event bus dispatches handlers outside the publishing request's scope, so durable consumers and plugin handlers never inherit a request's facts. Names come from identity through `AuditDirectoryRegistry`, read when the event is written (a rename shows from the next change on).
- Request country comes only from proxy headers documented by their vendors: `CF-IPCountry` (Cloudflare; `XX` = unknown is dropped, `T1` = Tor is kept; https://developers.cloudflare.com/fundamentals/reference/http-headers/), `CloudFront-Viewer-Country` (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/adding-cloudfront-headers.html) and `x-vercel-ip-country` (https://vercel.com/docs/headers/request-headers). They are only as trustworthy as the proxy in front. No IP address is stored; user agents are cut at 300 characters.
- Instance audit events go on their own stream `audit:instance` (core `AUDIT_STREAM`; catalogue `AuditEventPayloads` in shared, not part of `EventPayloads`): `auth.signed_in|sign_in_failed|signed_out`, `settings.changed`, `theme.installed|removed|default_changed`, `webhook.created|updated|removed`, `plugin.settings_changed` (the Discord notifier's settings among them). Only instance admins may follow the stream; plugins never receive it. Roles and ownership (`access.role_changed`, now with the role before), plugins (`plugin.*`) and access rules (`access.*` on map streams) were events already. Webhook URLs are kept as origin plus a fingerprint and secret-looking plugin settings (keys with token, secret, password, webhook, or ending in key or url) as `hidden (<fingerprint>)`, so a change shows without the credential. API tokens do not exist yet; their channel is modelled (`api` + token id) for when they do.
- Retention: the event log is no longer pruned by default (supersedes the 30-day default above). `eventRetentionDays` (instance setting, null = keep everything, set in the Audit tab) prunes hourly; refs go with their events. Replay, snapshots and durable consumers are unaffected: they read recent events or fall back to snapshots as before.
- Hash chain per stream: each row stores `prev_hash` and `hash` = SHA-256 over the previous hash and the stored text of every column; `event_stream.head_hash` is the newest. `POST /api/admin/audit/verify` walks every stream: the oldest stored row anchors the chain (retention may have pruned before it), every later row must point at the one before and hash to its value, and the last must be the recorded head. Rows from before the migration count as unchained.
- Histories: `GET /api/maps/:mapId/history` (viewer+), `/systems/:solarSystemId/history` (the system, its signatures and the connections touching it), `/connections/:connectionId/history`, `GET /api/admin/audit` (the instance stream, the audit stream and access rule changes of every map; with `mapId` only that map's access rules and webhooks, never its map state). Filters `accountId`, `characterId`, `solarSystemId`, `types` (exact or `prefix.*`), `since`; newest first, paged with an opaque `before` cursor (time, seq, stream). Exports (`/history/export`, `/api/admin/audit/export`, `format=csv|json`) stop at 50 000 entries; CSV cells starting with `=`, `+`, `-` or `@` get a leading `'` against formula injection.
- Reverts (`POST /api/maps/:mapId/history/:eventId/revert`, member+) run through the mapping use cases as the caller (so their own role checks apply), recorded with `revertOf`. Revertible: system added/updated/removed, connection added/updated/removed (a removed connection comes back with a new id and its attributes), signature added/updated/removed (with its link when the connection still exists), labels and map settings. A revert is refused (409) when a touched field no longer has the value the change gave it, when the change was already reverted or when nothing would change; character, plugin and access events are not revertible.
- Presence (`/ws`, never stored, not on the event log): the client sends `{op:'presence', stream, state}` patches (cursor and drag in map coordinates, an editing marker `{kind, id, field?}`, the selection) and `{op:'presence.leave'}`; the server answers the joiner with everyone else (`full: true`) and then sends changes coalesced per map at most 15 times a second (`PRESENCE_HZ`). Only signed-in accounts on a `map:` stream the socket follows may join, so the map's authorization and its re-checks apply; dropping the subscription, losing access or closing the socket leaves. Clients throttle to the same rate and re-join with their last state after a reconnect.

- Bookmark numbers (`{n}`, two-digit `{N}`): the number of a wormhole among the wormholes out of its parent system, so templates like `WH{n}` or `{n} {sig3}` label holes WH1, WH2, WH3 per system. The parent is the chain as `bookmarkChain` walks it (`chainTree` in shared, used by the server and the web app alike); stargates and bridges get no number, and a template that uses `{n}` shows nothing (or the temporary name) without one. Numbers are kept by the server per connection (`ConnectionDto.bookmarkNumber` and `bookmarkParent`, the system it counts out of; migration `mapping/0004_bookmark_numbers`), so they survive reloads and are the same for everyone. They change only through use cases inside the change's transaction (`renumberBookmarks`): after a connection is added, removed or changes type, a system is hidden or its status changes (a new home turns the chain), and after a numbering change. Each change is a `connection.updated` with the connection before it, so it is published and audited like an edit (fields "Bookmark number", "Numbered from"; a number change can be reverted); a connection added in the same change is published once, already numbered (`EventBatch` folds the update into the `connection.added`). Rules (`assignBookmarkNumbers`, domain): a wormhole keeps its number while it leads out of the same system; a closed sibling leaves a gap; a wormhole without a number takes the lowest free one, several at once in the map's order; with `renumberOnClose` the kept numbers close their gaps in their current order instead; renumbering on request numbers 1, 2, 3 in the order. Orders (`BookmarkOrder`): `found` (connection creation time, the default), `signature` (the signature in the parent system, A to Z, unknown last), `class` (of the system it leads to: HS, LS, NS, C1 to C6, then the rest, unknown last), `manual` (the current numbers); ties go by found. Because numbers are stable, the order decides where numbers go when several are given at once, when renumbering, and when the order itself changes (which renumbers every system); a newer hole that sorts first does not push older numbers. The map's `MapSettings.bookmarkNumbering` (`{ order, renumberOnClose }`, absent means found and gaps kept) is set with `PUT /api/maps/:mapId/bookmark-numbering` (manager+, `map.settings_changed`). Members may renumber (`POST /api/maps/:mapId/bookmark-numbers/renumber`, optional `parent`) and set a number by hand (`PUT /api/maps/:mapId/connections/:connectionId/bookmark-number`, swapping with the sibling that had it, up to the number of siblings or the highest number in use). By hand is a per-connection number edited through that route; the settings list the systems with two or more numbered holes, with up and down buttons, when the map's order is `manual` (shown to callers that pass `canEdit`, managers by default). A pilot's own order is a preference (`MapPreferencesDto.bookmarkOrder`): when it differs from the map's, that screen numbers the holes 1, 2, 3 in it on its own, and the settings say those numbers may not match the fleet's. Connections from before numbering are numbered once at startup by the system process `bookmark-numbers`. Signature edits do not renumber.

Static data has no planets or sun and no intel endpoint gives kills or jumps yet, so the header shows neither; `SystemActivity` is the slot for them. Ship type names are not in the data either: Local shows the type's icon from the image server next to the ship's name.
- Exits on nodes come from the routing API only (`exits` in the snapshot, `routes.exits_changed`): a known-space system the chain reaches by wormhole shows its nearest hub and jumps below it. `HubDistanceDto.space` (on an exit's `nearest`) says whether the shown route runs through one kind of space (`high` true sec >= 0.45, `low` above 0.0, `null`) or is `mixed` (any wormhole or Pochven system makes it mixed); only a single kind gets a coloured square. The client no longer derives exits itself.
- Telemetry (`packages/modules/telemetry`, `apps/server/src/modules/telemetry`, docs/telemetry.md): anonymous, on by default in production builds that carry a PostHog project key (`DEFAULT_TELEMETRY_KEY`, empty for now, so every build is inert until the maintainers fill it in), off in development and test, off with `TELEMETRY=off`, `DO_NOT_TRACK=1` or the admin switch; the environment beats the switch. Opt-out rather than opt-in because an opt-in heartbeat from self-hosted software counts almost nobody; what is sent cannot identify a group, a person or a place, and the admin card shows every payload.
- The module owns everything it needs: its environment (read by the Nest module, not `config.ts`), its tables (`telemetry_state`, `telemetry_notice`), its routes, its admin switch (stored in `telemetry_state`, recorded as the instance audit event `telemetry.changed`) and its lifecycle. Removing the line in `featureModules` removes it; other modules do not know it exists.
- Feature events come from two generic, read-only observation points instead of calls in other modules: `EventLogTaps` (platform), which the event log tells after commit about every event as written (with `before`) and the audit facts it was written under (so auto-mapping is told from people and a revert is counted once), and a global interceptor that reads successful requests on a fixed list of routes (`OBSERVED_ROUTES`: route computed, signatures pasted, ESI picker, waypoint, bookmark templates) from their enum inputs and counts.
- Allow-list first: every event and property is a zod schema of enums, booleans, buckets and small integers (`TELEMETRY_CATALOGUE`), and a PII check behind it refuses strings that are not short tokens or look like emails, IPs, UUIDs or long numbers, and numbers over 10 000 000 (all EVE ids are larger). Unknown server events are dropped and logged; a web batch with one unknown event or property is refused whole (400).
- Identity: the instance is a random UUID; an account is `u_` + 32 hex of HMAC-SHA256(per-instance random secret, account id). The HMAC is a port (`HmacSha256`), because modules do not import `node:`.
- No posthog-js: browser events go through `POST /api/telemetry/e` (signed-in accounts only), so stripping is guaranteed in one place, nothing third-party runs in the browser, no cookie or storage is used, and ad blockers do not skew the numbers. The browser's Do Not Track and Global Privacy Control turn its own events off.
- Sending: posthog-node behind the `TelemetrySink` port, batches of 20 or every 30 s, a 1000-event memory queue, gzip, flush on shutdown; its own retries are off and a `Backoff` around fetch (5 s doubling to 1 h, jitter) throws on network errors, 429 and 5xx so the batch stays queued. `before_send` strips `$ip`, GeoIP and `$set` and forces `$ip: null`, `$geoip_disable: true`, `$process_person_profile: false`. A per-instance cap of 300 events a minute drops the rest (counted on the admin card). No disk queue: a restart loses at most a few minutes of events.
- Demo instances send, with `demo: true` on every event, so previews show which features people try without counting as real usage.
- Heartbeat: checked hourly, sent when the last one is 23 h old (the first a minute after a new instance starts); counts accounts, characters and maps exactly and map contents (systems, connections, signatures, webhooks, Discord notification maps) as buckets; actives are accounts by `last_seen_at` and the characters of those accounts; the online peak is sampled every 5 minutes. It reads other modules' tables with plain counts in its adapter, each query failing soft to 0 (a plugin table that does not exist).

An unknown or forbidden section opens the first allowed one. The dialog code loads when it first opens. Invalid settings are configuration errors that stop the start, like the rest of the environment.

While telemetry is off the preload reads the environment and imports nothing of the SDK.

- Prometheus: `/metrics` on the instance's own port behind a mandatory bearer `METRICS_TOKEN` (min 16 characters), not a separate port: one port stays the rule, and an unset token cannot leave it open. The web proxy now forwards only requests no server route matches (`request.is404`), so server routes outside `/api` such as `/metrics` stay with Nest.

Both create database spans only under an active span (`requireParentSpan`), so the 1 s tracking ticks and consumer polls do not start traces of their own.
- ESI metrics come from undici's diagnostics channels (every `fetch` to `esi.evetech.net`, plugins included), folded to route templates (`/characters/{id}/location`); rate-limit gauges keep the last seen `X-Ratelimit-Remaining` per group and `X-ESI-Error-Limit-Remain`.
- The web app's server traces only (`<service>-web`, `src/instrumentation.ts` with `NodeSDK` and the undici instrumentation); the API server exports metrics and logs for both, as the web server's output goes through its logger. The API server passes `OTEL_SDK_DISABLED=true` to it while the API exports no traces.
- `PluginContext.metrics.delivery(channel, outcome)` (plugin SDK 1.x, additive) lets plugins count notification deliveries into `darkbeacon.notifications.deliveries`; discord-notify reports every post.
- `/api/ready` (database answers, no pending migration) joins `/api/health`, which keeps its meaning (process, database and web server answer) for the image's health check.
- Backups (`packages/modules/backups`, adapters in `apps/server/src/adapters/backups`, docs in `docs/backups.md`) are SQLite only; on Postgres the status says `supported: false` and the other routes answer 409 pointing at `pg_dump`.
- Snapshots use better-sqlite3's online backup API (`db.backup()`) on the server's own connection while it is held (`Database.exclusive()`, Kysely's single-connection mutex): no transaction is open during the copy, so the copy is the database exactly between two transactions, steps of 1024 pages yield to the event loop, and queries just wait. `VACUUM INTO` was rejected: on the only connection it is one synchronous statement that freezes the event loop (HTTP, WebSocket heartbeats) for the whole copy, and taking it off that connection needs a second connection plus a worker thread. A copy is switched to `journal_mode=DELETE`, quick-checked, gzipped (level 6) with a SHA-256, and stored with a JSON manifest; the CLI, a separate process, copies in one step so the server's writes cannot restart it.
- `Database` wraps the SQLite handle in `SqliteFile`, whose `forKysely` object forwards to whatever handle is open; a restore closes it, renames the staged file over `app.db` (staged next to it so the rename is atomic, stale `-wal`/`-shm` removed), reopens, migrates and checks, all inside `exclusive()`, so nothing that holds the `Database` has to be rebuilt. Any failure puts `app.db.rollback` back.
- Backup settings and history (schedule, retention, last success/failure/restore, the alert webhook) live in `BACKUP_DIR/backups.json` (mode 0600), not in the database: a restore replaces the database and must neither change the schedule nor forget a failure. Environment variables (`BACKUP_*`) are the defaults the admin tab overrides.
- Retention only removes automatic backups (scheduled, pre-restore, pre-migration), keeps the newest automatic one whatever the age limit says, and never touches manual ones. File names carry the UTC time, the app version and the schema version (count of applied migrations); validation compares the actual migration names, so "newer schema" means migrations this code does not know.
- A restore: validate (gunzip with a size limit, `PRAGMA integrity_check`, required tables, no unknown migrations) before anything changes; then maintenance, then the `pre-restore` backup (inside maintenance rather than before it, so nothing written in between is lost), then the swap. Refused files are audited but do not mark backups as failing.
- Maintenance mode is a platform service (`MaintenanceMode`) with participants modules register (event consumers pause and re-initialise their cursors from the restored database, plugins unload and load again, tracking and webhook retries skip ticks, the Discord bot forgets cached lists, the realtime gateway closes sockets). The HTTP gate (before the web proxy) refuses non-GET `/api` requests with 503 `unavailable` and answers page loads with a self-refreshing "Back in a moment" page; new WebSockets are closed with 1013. Backup routes and health stay open.
- After a restore the gateway closes every socket with `4100` (`RESTORED_CLOSE_CODE`); the web client drops the seqs it holds (they belong to the old database) and reloads the page, which renders from the restored data and signs in again where the session is not in the backup.
- A pre-migration backup is a startup hook the platform runs before pending migrations on an existing database (`onBeforeMigration`, registered by the backups module file), so the platform does not know about backups; its failure is recorded and logged but does not stop the server.
- Restore confirmation is typing `RESTORE` (there is no instance name), checked in the UI and again by the server for every restore request. Uploads are `multipart/form-data` streamed to disk with `@fastify/busboy` (no body buffering), limited by `BACKUP_MAX_UPLOAD_MB` and 10x that once decompressed.
- Alerts for `backup.failed` and `backup.restored` (and `backup.completed` when asked for) go through the core `NotifierRegistry` as instance notifications (`mapId: null`) and to an optional alert webhook: Discord webhook URLs get an embed, anything else a small JSON body. Only the host is ever shown or audited.
- The `darkbeacon` command in the image (`/usr/local/bin/darkbeacon` -> `apps/server/dist/cli.js`) runs `backup list|create|verify|restore`; it acts as the system actor `cli`. `restore` refuses while the server answers on `PORT` in the same container, so it runs in a one-off container on the stopped server's volume.
- Off-site copies are out of scope; `BackupStorage` (list/get/put/fetch/read/remove of manifests and files) is the port an S3-compatible adapter would implement.
- Backups contain the database only: `secret.key` and `/data/plugins` are not included (the key would make the encrypted tokens in a copied backup readable); docs/backups.md says to keep the key separately.
- Shares between maps (`packages/modules/sharing`, `@darkbeacon/sharing`; Nest `SharingModule`). A share names its source and target as origins `{ instance, mapId }` (`local` for this instance) and carries a level (`read`, `read-write`) and scopes. The source map's admins offer (`POST /api/maps/:mapId/shares`, target by id or by address), the target map's admins accept (`…/:shareId/accept`, optionally keeping only some scopes) or decline; one person who administers both maps shares in one step. Either side revokes (`DELETE`); the source's admins change level and offered scopes, the target's admins narrow what they receive (never past the offer) and hide a share for now (`PATCH`). Offers, acceptances, changes and revocations are `map.share.offered|accepted|changed|revoked` (the `MapShareDto`) on both maps' streams, audited there. A map cannot be shared with itself, twice with the same map, or when it is a composite (it has nothing of its own; shares are never passed on, so they cannot loop). Shares live in `map_shares` without foreign keys into mapping; a deleted map takes its shares with it (the sharing module follows `map.removed`).
- Share scopes are `shareScope` in `packages/shared/src/share-scope.ts` (also for public maps and, later, federation): `topology` (systems, connections and their kind; always on), `connectionStatus` (mass, time and EOL, size, mass saved, dangerous, bubbled), `signatures`, `intel` (system status, tag, custom name, notes; sensitive), `characters` (tracked characters' location, ship, online; sensitive), `labels` (bookmark labels, i.e. temporary names). New offers default to topology, connection status and signatures. A map's label assignments and locks are `local`: they never leave it. Scopes are enforced where data leaves a source (`projectEntry` in the source adapter), so nothing outside them reaches the merge, the stored view, the derived events, snapshots, routing, history or provenance; writes through a share are refused for fields outside its scopes (what a map cannot read it cannot change).
- A map that merges others is a composite (`MapDto.kind = 'composite'`, chosen when creating a map; mapping refuses edits of its own rows with a 409) or a standard map with accepted shares. It merges its own objects (source `self`, all scopes, read-write) and its active, not hidden shares in acceptance order. Its snapshots then carry `sources` (`MapSourceDto[]`, `self` first) and its systems, connections, signatures and characters are the merged ones, each object with a `provenance` (the sources holding it, `updatedBy`/`updatedAt` of the newest change, `writable` when the map itself or a read-write share holds it). Viewers of a merged map gain nothing on its sources: no access, no history, no ids of their rows.
- Merge rules (`ChainMerge`, framework-free): systems are keyed by solar system id, connections by their unordered pair (`<low>-<high>`), signatures by system and code (`<system>:<code>`), characters by id. Every field is last-writer-wins by its own change time, a tie going to the earlier source. A pair is one hole unless typed signatures name different wormhole types on it (never K162): then each type is its own hole and untyped copies join the oldest; the oldest keeps the plain id `c:<pair>`, the others are `c:<pair>:<type>`. Merged ids are made from the keys (`<system>`, `c:…`, `s:<system>:<code>`, character id), so they never name a source's row and survive restarts. A copy counts while it changed after the newest deletion any source knows of its key, so an older copy never brings a deleted connection or signature back and a newer sighting does. Hiding a system on a source is not a deletion: the system (and the connections that went with it) stays on the merged map while another source shows it. Merged connections are drawn from the lower system id; `bubbled` crosses the wire as `low`/`high` and is turned back into source/target.
- Mapping keeps per-field change times (`field_times` JSON on systems, connections and signatures, stamped by the repositories on every update with the change's `updatedAt`; a missing field has not changed since the row was created, which is also what rows from before the migration claim) and tombstones (`map_tombstones`) of deliberate deletions: removing a connection, removing a signature, a paste in replace mode, a changed signature code. Port `ChangeStamps` in mapping; maps gain a `kind` column (migration `mapping/0005_change_stamps`, after main's `0004_bookmark_numbers`).
- Positions on a merged map are its own layout (`chain_layout`): a system new to it lands where its newest source position says, moved down until it covers nothing (`placeFree`, 360 by 150 px steps), the map's own systems first so they keep their places. Dragging on a merged map (any member) moves only its layout, never a source.
- Realtime: sources sit behind the `ChainSource` port. Changes of local maps reach the merger through the event bus (`SharingFeed`): each event names what to read again (`feedSignal`); the merger reads the current state of those keys from the source (never the payload, so late, repeated or reordered events are harmless), merges only the touched objects and their dependants (a system's connections and signatures, a hole's signatures) and publishes the difference as ordinary `system.*`, `connection.*`, `signature.*` and `character.tracked|untracked` events on the merged map's own stream (actor and audit channel `system:sharing`, `mergedFrom` the source map) with its own seq, so replay by `sinceSeq` and snapshots work as for any map. Work on one merged map runs one at a time and a burst is merged in one pass. What its viewers were given is stored with the events in one transaction (`chain_views`, `chain_view_entities`), so snapshots read it consistently with the stream head; startup (`rebuildAll`) and every grant change merge from scratch and publish only what differs from what was stored, so nothing missed while the server was down is lost. `map.sources_changed` follows any change of the source list; the browser reloads the snapshot then.
- On a merged map the browser applies only the merged view's events (by `system:sharing`, or carrying a provenance) to systems, connections, signatures and characters; the map's own events about its rows are history. Mapping's snapshot, connection intel (without passages: who jumped stays with the sources), signature list and routing's chain read the merged chain through `ChainOverlaySlot`, which sharing fills (sharing depends on mapping, not the other way round).
- One API for every map: on a merged map the map routes for systems, connections and signatures change the merged chain (`MergedWriteRouter` at the HTTP edge). A change goes to every source holding the object that takes writes (the map itself, read-write shares), each getting only the fields its scopes allow; it is refused (403) when only read-only sources hold the object or when no holder may take a field. New systems go to the map's own objects, on a composite to its first read-write source; a new connection goes to the writable sources holding either system (each adds the system it lacks next to the other), else like a new system; a signature or a paste to the writable sources holding its system. Deleting through a merged map deletes from writable sources only; their newer tombstone then hides older read-only copies. At the source the change runs through mapping's use cases as the person (counted as a member of that map unless blocked there) and its audit record carries `via` (the merged map); history entries show `via` and `mergedFrom`, the CSV export a `via` column.
- Auto-mapping records a jump once: when a map merged into the character's map also tracks the character, that map records it and the merged map sees it through the merge; otherwise a standard map records it on its own objects and a composite writes it through like a new connection.
- Federation-ready contract (no remote transport yet): `ChainSource` (`read(scopes, selectors?)` -> `ChainDelta`, `write(command, context)`, which may refuse) is all a merged map knows of a source, and `ChainSources` resolves origins (only `local` today). `ChainDelta` (zod in shared, `v: 1`) is `{ origin, scopes, full, entries, at }`; an entry is `present` (`born` and `fields` of `{ v, at }`), `absent` (the source does not hold it) or `deleted` (a tombstone `at`), keyed by the stable keys above and cut to the scopes at the source. `ChainCommand` names objects by the same keys and wire field names (`FIELD_SCOPES`), so a remote source can apply or refuse a write the same way. Provenance names maps (origin, name, the instance name for remote ones), never accounts: account ids of another instance mean nothing here (shared characters carry `accountId: 'shared'`). A remote adapter will implement `ChainSource` over HTTPS/WebSocket and push its changes into `ChainMerger.sourceChanged`.
- Map settings gain a Sharing section (`?settings=sharing`, admins; telemetry section `sharing`): maps shared with this one (accept or decline an offer, allow writes a source now offers, what this map receives, show or hide, on a composite which read-write source takes its new systems, stop merging) and, on standard maps, where this map is shared (level, what is shared, stop sharing) and a form to share it with a map picked from the admin's maps or by address. Scopes are checkboxes with one line each; intel and characters are marked Sensitive. New maps may be created as a composite. On a merged map the system sidebar shows one quiet line of provenance under its header and a connection's context menu under its title; edit actions show only for objects a writable source holds (locks and labels for the map's own objects, and for every system of a composite); the top bar has a "Merged maps" menu to hide sources in this browser. Nothing is drawn on nodes or edges.
- The demo seeds "Corp A chain" and "Corp B chain" (overlapping on J130256 and J130026 and disagreeing about the mass of the hole between them) and the composite "Alliance chain" merging both (Corp A read-write with intel, Corp B read-only); `/` still opens "Demo chain".
- Merged events on a map with objects of its own are copies: the merge writes them as `system:sharing-copy` (`MERGE_COPY_ACTOR_ID`, `isMergedCopy` in shared), and webhooks and plugins (live handlers and durable consumers, the Discord notifier among them) skip them, so such a map notifies about its own changes once. On a composite the merge's events (`system:sharing`) are the map's own news and reach its webhooks and plugins like any map's, so Discord notifications fire on every map they are configured on, composites included. The browser and the sharing feed take both ids as the merge's.
- A composite picks where its new systems and connections go: a read-write source its admins mark "Send new systems here" (`defaultWrite` on the share, one per composite, cleared when the share drops to read-only), else its first read-write source.
- Raising an accepted share from read to read-write needs the target's consent again: the source's admins offer it (`offeredLevel`), the share keeps writing nothing until the target's admins accept (`POST …/accept` on the active share); lowering it, or one person administering both maps, applies at once.
- Tombstones are forgotten after 30 days (hourly, `TOMBSTONE_DAYS`): a copy older than that on another map could show a deleted connection or signature again, which wormholes (at most 48 hours) and their signatures do not outlive.
- A composite keeps notes, label assignments and locks of its systems itself (`chain_local_fields`, written by the map routes on the composite): they win over what its sources say in its view, are published like any change of the map, and stay with it when sources change. A locked system on a composite cannot be moved or hidden there. On a standard map that merges shares its own rows are a source like the others (last writer wins). Label ids are the composite's own and are not checked against its label list.
- Bookmark numbers (`{n}`) stored on connections belong to their source maps and are not shared: a merged map counts `{n}` in the browser in the map's numbering order over the merged chain, the manual order and "Renumber now" are hidden on composites, and setting or renumbering numbers on a merged map is refused (409).
- Backups and restores need nothing extra: the sharing tables are in the database file; while a restore runs, sharing pauses (`MaintenanceMode` participant), and after it forgets what it kept in memory and builds every merged map from the restored data.
- Provenance never names accounts, only maps (and instances).
- Every route in `routes.ts` declares `scope` (required, so a new route cannot ship without deciding): `none`, `session` (browser sessions only; keys are refused: sign-in, sessions, key management, the Discord bot token, plugin pages, presence, preferences) or `{ resource, action }` on the map in the path (`global` for creating maps). The grammar and its evaluation live in `packages/shared/src/scopes.ts` (pure, used by the edge, the MCP tools and the web app); `docs/api.md` describes it. `federation:*` is parsed but refused (reserved).
- Credentials narrow, never widen: core's `Actor` gains an optional `CredentialGrant` (key id and name, channel `api`/`mcp`, scopes, read-only, and per-map role caps computed from the scopes with `scopeRoleCaps`); `AccessService.roleOf` returns `capMapRole(actor, mapId, ownRole)`, so every use case enforces it without knowing about keys. A personal token is an `account` actor with a grant (its owner, role re-resolved per request); a service key is an `apiToken` actor with its own roles (`roles.allMaps`, `roles.maps`) and a grant; a public visitor is a `public` actor, viewer of one map. `requireInstanceRole` accepts service keys with the admin role; `requirePrincipal` (accounts and service keys) replaces `requireAccount` where static data is read.
- API keys are the `@darkbeacon/api-keys` module. Tokens `dbk_pat_`/`dbk_svc_` + 12 lookup + 32 secret + 6 CRC32 checksum characters (base62); the row keeps the lookup and HMAC-SHA256 of the secret with a pepper derived (HKDF, salt `darkbeacon`, info `api-keys`) from SECRET_KEY, compared in constant time; argon2id was not chosen because the secret is random (~190 bits) and a slow hash would only cost CPU per request. Last use is written at most once a minute per key (or when the address changes). Key changes are audit events `api_key.created|updated|rotated|revoked` on `audit:instance`, without lookup or hash.
- Bearer tokens are resolved by `ActorResolverRegistry.useBearer` (installed by the api-keys module); with `Authorization: Bearer` cookies are ignored, an invalid key is a 401 with `WWW-Authenticate: Bearer realm="darkbeacon", error="invalid_token"`, a missing scope a 403 `insufficient_scope` naming it. The guard finds the route's contract entry by method and Fastify pattern (`route-index.ts`); routes outside the contract refuse keys. Cookies count only for same-origin requests (no `Origin`, the public origin or the request's host), whatever CORS allows.
- Limits are in-process token buckets (`RateLimiter`): 300 requests a minute per key unless the key sets its own, ten failed bearer tokens a minute per address (then 429), 120 anonymous public reads and anonymous MCP calls a minute and 30 public subscriptions a minute per address. The client address is the socket's unless the socket is private (a proxy on the host or a private network), then the right-most non-private `X-Forwarded-For` entry.
- CORS is an `onRequest` hook for `/api` and `/mcp`: origins listed in the instance setting `apiCorsOrigins` (read on every cross-origin request) get `Access-Control-Allow-Origin` and preflights; never `Allow-Credentials`. Other cross-origin preflights get 403.
- `/api/v1/...` is rewritten to `/api/...` by Fastify's `rewriteUrl`, so integrations use a stable prefix; versioning and deprecation policy in `docs/api.md`. `API_VERSION` (`info.version`) is the contract's semver.
- OpenAPI 3.1 and AsyncAPI 3.0 are generated by `packages/shared/src/openapi.ts` from `routes.ts` with zod 4's `z.toJSONSchema`: every exported DTO schema is a named component (`<Name>`, and `<Name>Input` where the request shape differs: defaults, transforms), security per operation (`sessionCookie`, `bearerAuth` with the scope as role name), `x-darkbeacon-auth|scope|map-role`, webhook payloads under `webhooks` with one `Event_<type>` schema per event type from `EVENT_DATA_SCHEMAS` (a `Record` over every event type). Routes carry optional `summary`, `status: 200` (for POSTs that answer 200; otherwise POST with a body is documented as 201), `download`, `upload` and `contentType`. A server test compares the routes Fastify registered with the contract both ways (bundled plugins' own routes excepted).
- The API reference at `/api/docs` is Scalar's standalone bundle (`@scalar/api-reference` 1.72.1, served from `node_modules` under `/api/docs/assets/*` with a small init script), configured without default fonts, telemetry, MCP or agent features, under a CSP that allows only the instance's own origin.
- Public maps are the `@darkbeacon/publishing` module (Nest `PublishingModule`; table `public_link`, migration `publishing/0001_public_link`, one row per map: enabled, token, slug, scopes, noindex, MCP mode). Visibility uses the shared `ShareScope` vocabulary (`share-scope.ts`: topology, connectionStatus, signatures, intel, characters, labels; `SENSITIVE_SHARE_SCOPES` intel and characters), defaults topology + connectionStatus. The token is stored as is (it is the capability shown to map admins); 32 base62 characters. Changes are the map event `access.public_link_changed` (no token), so they are in the map history and re-check subscriptions.
- The public view is read with a `public` actor through the realtime snapshot providers (the mapping, tracking and routing use cases) and cut down by a whitelist projection (`projectSnapshot`, `projectEvent`): unshared fields are blanked to neutral values so DTOs keep their shape, unshared parts left out, events forwarded only for what is shared, with the actor `system:darkbeacon`. Connection status off blanks mass, time and size to fresh/normal/large; intel covers notes, status, tags, custom and temporary names, danger and bubbles and the map's own hubs in exits.
- Realtime view streams: a stream kind may declare `view` (source stream and per-event projection) and `admit` (checked on subscribe only); the hub indexes subscriptions by source, reads and replays the source stream, and advances the seq over events the projection drops. `public:<token>` is such a stream; `access.*` events on the source re-check its subscribers, and `access.public_link_changed` reaches public viewers as an empty event meaning "read the view again". Credentials follow `map:` streams only with read scopes on every resource there.
- MCP: `apps/server/src/mcp` (a driving adapter; `McpModule`, imported like a feature module) on `@modelcontextprotocol/server` 2.1.0 (`createMcpHandler`, stateless, JSON responses, legacy 2025-era clients served statelessly), spec 2026-07-28. `/mcp` is excluded from the `api` prefix and from the web proxy. Each request builds the server for its caller (API key actor, or anonymous) from the use cases (mapping, routing, audit, the realtime snapshot) and the universe catalog; tools check the key's scope per call and map, write tools are registered only for keys with write scopes, anonymous callers get read tools over the public projection. Instance `mcpMode` (`off` default, `authenticated`, `public`) and the map's own mode (default `authenticated`) bound it; anonymous agents see maps whose mode is `public` while their link is on. Requests are rebuilt without `Authorization` and `Cookie` for the SDK. Clients authenticate with API keys or OAuth (next entry).
- The SDK client (`@modelcontextprotocol/client` 2.1.0, dev dependency) is imported at run time in the MCP test: its packages export a `source` condition pointing at TypeScript that does not compile under this repository's settings (`tsc -b` resolves `source` for the workspace).
- Fastify routes are recorded as they are registered (`registeredRoutes(app)`, an `onRoute` hook in `createApp`) for the contract test.
- OAuth 2.1 for `/mcp` is the `@darkbeacon/oauth` module: Darkbeacon is the authorization server of its own MCP endpoint (issuer = `PUBLIC_URL`, resource = `PUBLIC_URL/mcp`). Metadata at `/.well-known/oauth-protected-resource[/mcp]` and `/.well-known/oauth-authorization-server` (also answered at `openid-configuration`), served by Nest outside the `api` prefix and the web proxy. Public clients only; Client ID Metadata Documents (HTTPS, public addresses, no redirects, 16 KiB, re-read after an hour) and RFC 7591 registration. The authorization endpoint is the web page `/oauth/authorize` backed by `GET/POST /api/oauth/authorize` (session only); the consent may narrow to picked maps (`narrowToMaps`) and read-only; `admin:` scopes are dropped; no scope asked means `*:read account:read universe:read`. Codes: 5 minutes, single use, S256 PKCE, bound to client, redirect URI and resource; a replay revokes the approval. Tokens `dbk_oat_` (1 hour, `/mcp` only) and `dbk_ort_` (30 days, rotating, reuse revokes the approval), stored as HMACs with their own pepper (`oauth-tokens`). An access token is the approving account with a `CredentialGrant` of kind `oauth`, channel `mcp`, the client's name, instance role `user`. Approvals (`oauth.grant_created|revoked`) are in the instance audit. Bearer resolvers register per token prefix (`useBearer(prefixes, resolver)`). The token and registration endpoints and the metadata answer CORS for any origin; Nest's own form parser reads the token request.
- Public links and shares between maps are two modules: `@darkbeacon/sharing` (map to map, composites) and `@darkbeacon/publishing` (the public link and the map's MCP reach; routes `/api/maps/:mapId/public-link[/regenerate]`, Map settings section `public`, its own Nest module, table and migration folder). Both use the one `ShareScope` vocabulary, and a field belongs to the same scope in both (sharing's `FIELD_SCOPES`): danger and bubbles are connection status, the temporary name is `labels` (bookmark labels), signature notes travel with signatures, label assignments and locks never leave their map. Label definitions are not public; `labels.changed` is never forwarded.
- A public link or an agent on a map that merges others reads the merged chain through mapping's snapshot (sharing's overlay), so what each share lets the map see is applied first and the link's scopes on top; provenance and `sources` are left out by the whitelist projection, and `map.sources_changed` reaches public viewers as an empty event ("read the view again"). Writes by keys and MCP tools on such a map go through `MergedWriteRouter` (exported by mapping) to sharing's write-through like the REST routes, so its 403 (read-only source, scope not shared) and 409 (locked, not reachable) hold for keys and agents too. Short ids in MCP answers are the last 8 characters of v7 ids; merged ids (`c:<pair>`, `s:<key>`) are given whole, and a short id that matches several objects is refused.
- Labels and Tags, as the product owner named them: **Tags** are the map's coloured markers with descriptions (Staging, Sites, Hostile, Exit), stored as `MapDto.labels` / `MapSystemDto.labelIds`, event `labels.changed`, route `PUT /api/maps/:mapId/labels`; the data keeps those names to avoid churn, everything users see says Tags. **Labels** are Wanderer's labels: the map's ordered list `MapDto.systemLabels` (`{ id, name ≤ 8, description ≤ 120 }`, every map starts with WH1, WH2, WH3 with the fixed ids `wh1`-`wh3`; existing maps get them in migration `mapping/0006_system_labels`), set on systems as `MapSystemDto.systemLabelIds`, plus one free-text `customLabel` (≤ 16) per system; event `system_labels.changed`, route `PUT /api/maps/:mapId/system-labels` (manager+, replaces the list; systems lose labels that are gone, as with Tags). Labels are neutral text; above a node the order is Labels, custom label, bookmark code, Tags.
- The free-text `tag` of a system is no longer shown or edited (menu, sidebar, header, tooltip); the column, DTO field and wire field stay for compatibility and old history.
- Labels cross maps by name, not id: shares send the names of a system's Labels (`systemLabels`) and its `customLabel` under the `labels` scope (with the temporary name); a merged map shows the names its own list has (any case) and drops the others; edits on a merged map go back to sources as names and a source keeps the ones it has a Label of. A map's Labels list changing rebuilds the maps that merge it. Tags stay `local` (never leave their map; a composite keeps its own).
- `{labels}` in bookmark templates is a system's Labels in the map's order, then its custom label (`WH1 bait`).
- Wanderer import mapping (for the importer): Wanderer's map-level `system_labels` (JSON `[{ id, name, color, description }]` on the map; when empty Wanderer uses its defaults A, B, C, 1, 2, 3 with ids `a`, `b`, `c`, `1`, `2`, `3`) become the map's Labels in order: ids kept, names trimmed and cut to 8 characters, descriptions cut to 120, colour dropped (Labels are neutral), a later duplicate name (any case) merged into the first. A system's `labels` (JSON `{ labels: [ids], customLabel }`, or the older comma list of ids) becomes `systemLabelIds` (ids through the imported list, unknown ones dropped) and `customLabel` (trimmed, cut to 16, empty is null). Wanderer's single letter/digit `tag` of a system becomes a Darkbeacon Tag of that name set on the system (`labelIds`), created in the map's Tags when missing (neutral grey, no description); Darkbeacon's own `tag` column is not written.
- Jump planner: the one place Darkbeacon goes beyond Wanderer. `/jump` is its own map, of all known space, where a capital's jump route (jump freighter, titan, carrier…) is planned from A to B. Its module is `packages/modules/jumps` (domain: ship rules, formulas, the indexed space and the planner; application: `JumpPlanner`; port: `JumpSpaceSource`), wired in `apps/server/src/modules/jumps`; the routes are `GET /api/jumps` (ships, dataset version), `GET /api/jumps/universe` (the map) and `POST /api/jumps/plan`.
- The k-space dataset is `packages/sde/data/kspace.json` (built with the universe from the same SDE zip, `pnpm --filter @darkbeacon/sde data`; an operator's `DATA_DIR/kspace.json` wins, as for `universe.json`): the 5255 known-space systems the stargate network reaches plus Pochven (the Jove regions are left out: 217 systems have no stargate, the 13 of UUA-F4 that do only link to each other), columnar (id, name, region, true security, x/y/z in light years with 4 decimals, flags 1 NPC station / 2 Pochven / 4 Zarzakh), the 6973 stargates as index pairs and the 56 published ships with a jump drive. 354 KB, 125 KB gzipped; the server sends it gzipped with an ETag, and as `?v=<sha256 prefix>` with `Cache-Control: private, max-age=31536000, immutable`, so a browser downloads it once per dataset.
- Light years are the SDE's metres over 9 460 730 472 580 800 (the IAU light year). The map is top-down like the in-game star map and Dotlan: x to the east, z to the north (screen y = -z), so Jita is north of Amarr and east of Dodixie.
- Ship facts come from the SDE (build 3586130, 2026-10-07), not from tables: `jumpDriveRange` (867, base ly), `jumpDriveConsumptionAmount` (868, isotopes per ly), `jumpDriveConsumptionType` (866: 16274 helium, 17887 oxygen, 17888 nitrogen, 17889 hydrogen), `jumpFatigueMultiplier` (1971: 0.1 jump freighters and Rorqual, 0.25 black ops; the traits say "90 %/75 % reduction to effective distance traveled for jump fatigue"), `jumpPortalConsumptionMassFactor` (1001: titans 1e-9, black ops 1.35e-7) and hull mass. Hulls by SDE group: 30 titan (3 ly, 3000/ly), 659 supercarrier (3, 3000), 547 carrier (3.5, 3000), 5120 command carrier (3.75, 3000), 485 dreadnought (3.5, 3000), 4594 lancer dreadnought (4, 3000), 1538 force auxiliary (3.5, 3000), 883 Rorqual (5, 4000), 902 jump freighter (5; Ark 8800, Rhea 10 000, Nomad 8200, Anshar 9400), 898 black ops (4, 700). These match https://wiki.eveuniversity.org/Jump_drives (dreadnought 3.5/7, command carrier 3.75/7.5, lancer 4/8, supercarrier 3/6, jump freighter 5/10, black ops 4/8, Rorqual 5/10).
- Range = base x (1 + 0.2 x Jump Drive Calibration): the skill's `jumpDriveRangeBonus` is 20 % per level, "at the maximum of level five the range is doubled" (wiki.eveuniversity.org/Jump_drives). A system is in range when the straight 3D distance is at most that.
- Fuel per jump = isotopes per ly x ly x (1 - 0.1 x Jump Fuel Conservation) x (1 - 0.1 x Jump Freighters, jump freighters only), rounded up to whole isotopes (the rounding is ours; the game shows whole units). Sources: the skills' SDE attributes (`consumptionQuantityBonusPercentage` -10), the jump freighters' trait "10 % reduction in jump fuel requirement" per level, and the wiki ("half the fuel at the maximum level of five").
- Jump fatigue and the activation timer follow https://wiki.eveuniversity.org/Jump_fatigue and /Jump_drives (Phoebe, Nov 2014, with the March 2018 caps from the dev blog "Sovereignty Warfare & Jump Fatigue Changes Coming In The March Release"): fatigue after a jump = max(fatigue before, 10) x (1 + effective ly), capped at 300 minutes; the activation timer = max(1 + effective ly, fatigue before / 10), capped at 30 minutes; effective ly = ly x `jumpFatigueMultiplier`. Fatigue falls a minute per minute. The worked carrier example of that page (5 ly jumps: 6 min / 60 min, 6 min / 5 h, then about 30 min / 5 h) is a test. The September 2026 update (patch notes 24.01, checked 2026-10-12) changed nothing here.
- Defaults are Jump Drive Calibration V, Jump Fuel Conservation IV and Jump Freighters IV: range is what decides whether a route exists, and overstating fuel skills would make pilots carry too little.
- Where a jump may land: a cyno must be possible there. Not in high-sec (true security 0.45 and up, routing's rule; "Cynos cannot be lit in high-sec"), not in Pochven (region-wide cyno jammers; "Jump drives cannot be used to enter Triglavian space, only to exit", wiki.eveuniversity.org/Pochven), not in Zarzakh (the EVE support article "Zarzakh": jump drives, conduit jumps and jump bridges do not work inside it and capitals are blocked from its gates), never wormhole space (not in the dataset; "jump drives cannot jump to systems in wormhole space"). Jump drives start anywhere in known space but Zarzakh, Pochven included. Cyno jammers (Tenebrex) and incursions change by the hour and are not known; the planner cannot see them.
- Who may be where (wiki.eveuniversity.org/Capital_ships, /Jump_Freighters): true capitals (carriers, dreadnoughts, force auxiliaries, supercarriers, titans, the Rorqual) never in high-sec; jump freighters may be there and "can jump out of highsec space"; black ops are battleships and go anywhere. Capitals take stargates in low and null-sec but not into high-sec, not in Pochven ("Capital ships cannot use stargates") and not into Zarzakh ("Capital sized ships, including freighters but not the Orca"). A start a hull cannot be in, or a destination it cannot reach, is answered as `origin_not_allowed` / `destination_not_allowed` with a sentence.
- Cyno kinds per hull come from the SDE beacon lists (`jumpDriveTargetBeaconTypelistID`): capitals 341 (normal cynos), jump freighters 343 and the Rorqual 348 (normal and industrial), black ops 342 (normal, covert and industrial). The planner names the cheapest one to light: industrial for jump freighters and the Rorqual, covert for black ops, normal for the rest.
- Route search: Dijkstra over (system, phase) with a lexicographic cost: fewest legs (jumps, gates and Ansiblex bridges), then fewest jumps, then (asked for) fewest stops without an NPC station, then fewest light years (= fuel, one hull per route), then the least fatigue (sum of log(1 + effective ly), since fatigue multiplies). Gates come only after the last jump (`gates: 'finish'`, the default; `never` turns them off): that is how a jump freighter reaches Jita or Amarr, and it keeps routes from being gate trips with a jump in between. Outlaw routes never enter high-sec, as the routing module's `outlaw` mode. Avoided systems and regions are never entered (the start and the destination excepted). A plan takes 10-40 ms on the full dataset (JS, one core).
- Real routes as a sanity check (Ark, skills V/IV/IV): Ignoitton (low-sec, 3 gates from Jita) to Ami (low-sec, 3 gates from Amarr) in 3 jumps, 20.19 ly, 63 969 helium; Jita to Amarr in 3 jumps and 3 gates; Avatar from 1DQ1-A to VFK-IV (59.7 ly apart) in 13 jumps through empire low-sec, at the 5 hour fatigue cap.
- The schedule assumes each leg is made as soon as the activation timer allows; "Keep fatigue under" waits longer before a jump so fatigue after it stays under the cap (wait = fatigue - cap / (1 + effective ly)); when even a rested pilot would end above it, the leg says so. Gate legs take no time in the schedule (fatigue keeps running down meanwhile, so it is an upper bound).
- Ansiblex bridges are the pilot's own list (one per line, two system names), both ends in null-sec and at most 5 ly apart (wiki.eveuniversity.org/Ansiblex_Jump_Gate), usable by jump freighters, the Rorqual and black ops only: "Removed the ability for capitals to use an Ansiblex Jump Bridge. Rorquals, Freighters, and Jump Freighters can still use Ansiblex Jump Bridges." (patch notes 24.01, 2026-09-22.1). They cost no isotopes and add no fatigue (no source says they do; the capacitor and alliance-only rules of September 2026 are the owner's business), but wait for the activation timer like any jump bridge. Pairs the hull cannot use are listed back with the reason.
- Bridges: a titan's Jump Portal Generator and a black ops' Covert Jump Portal reach as far as the ship jumps; the bridge fuel of a leg is mass bridged x `jumpPortalConsumptionMassFactor` x isotopes per ly x ly x (1 - 0.1 x Jump Fuel Conservation), as wiki.eveuniversity.org/Jump_drives gives it ("Mass×Portal Consumption Mass Factor×Base cost×Skill mod×Distance in LY"). The planner shows it per leg for a tonnage the pilot enters; who may be bridged (covert ships for black ops) is the pilot's call.
- The web map is a plain 2D canvas (no library): one path per security colour (the game palette in `SECURITY_COLORS`), stargates as one path, culling to the screen, labels placed on a coarse grid so they never overlap (region names below 16 px per ly, system names from 22), redrawn only when something changed. Pan by dragging, zoom with the wheel or a pinch; a click pins a system card with Start here / Destination / Avoid. The range is drawn as a disk around the start (or the leg under the pointer) and systems a jump cannot reach from there are dimmed until a route exists.
- The planner keeps the ship, skills and options in `localStorage` (`dbk.jump-planner.v1`, a convenience) and the start, destination and ship in the address (`/jump?from=Ignoitton&to=Ami&ship=Ark`), by name, so a link to a route can be shared. `/` focuses the first empty system search, Esc closes the system card or clears the route.
- Telemetry: `jump_planned` (`hull`: the hull class, `legs`: a bucket, `0` when there was no route) from `POST /api/jumps/plan` through the observed routes, and `page_viewed` gains `jump`. Hull classes are snake_case (`jump_freighter`, `black_ops`, `command_carrier`, `force_auxiliary`) because telemetry only lets lowercase tokens through.
- Jump mass facts, all from SDE build 3586130 (`dogmaAttributes.jsonl`, `typeDogma.jsonl`, `types.jsonl`) unless named: a ship's hull mass is its type's `mass`; an active afterburner or microwarpdrive adds `massAddition` (attribute 796, "adding mass to a ship via an afterburner or MWD"): 500 t for 1MN/5MN, 5 000 t for 10MN/50MN, 50 000 t for 100MN/500MN, 500 000 t for 10000MN/50000MN, the same for every meta level of a size (T1, compact, enduring, restrained, T2, faction, officer; abyssal modules list none of their own and are not modelled). Higgs Anchor I in every size (group 1308) has `massBonusPercentage` (1131) +100; the Zero-Point Mass Entangler (49099, group 2008) -80 and fits heavy interdiction cruisers (group 894) and the Odysseus (89607) only. Dogma applies additions before post-percent modifiers, so a jump weighs (hull + prop) x 2 with a Higgs Anchor and x 0.2 with the entangler on; one bonus and one malus each count in full ("Negative and positive effects are stacking-penalized separately", https://wiki.eveuniversity.org/Stacking_penalties). The builder refuses an SDE where prop modules of one size add different masses. Siege and industrial cores (`siegeMassMultiplier`) cannot jump wormholes while active and are left out, as are armour plates (always-on `massAddition`): a custom mass covers them.
- `wormholes.json` gains `ships` (every published ship: name, SDE group, hull class, prop size from `rigSize` 1547 — rookie ships and corvettes without one take the small size —, no prop for hulls without mid slots (`medSlots` 13) except strategic cruisers, whose slots come from subsystems, `rigs` from `rigSlots` 1137, whether the entangler fits) and `massModifiers` (`prop` per size, `higgsPercent`, `entanglerPercent`). Rebuilt from the same SDE build, so the rest of both files is unchanged. Ship pickers search these names (`GET /api/universe/ships`), never ids.
- How the game counts a jump: the mass the ship has when the jump is made, an active prop module included ("hot"); a hole that collapses does so behind the ship that closed it ("As you pass through the wormhole you realize that it collapses behind you", https://wiki.eveuniversity.org/Wormhole_Community_Static_Rolling_Guide, archived but still how rolling works; the mass check moved to the moment the jump is pressed, https://forums.eveonline.com/t/changes-to-wh-mass/221528). A hole's real total is its type's ±10 % ("2,000,000,000 kg ± 10%", https://wiki.eveuniversity.org/Wormholes); the statuses mean more than 50 %, less than 50 % and less than 10 % remaining (same page). Polarization: "You may not jump through a wormhole in the same direction twice within five minutes", per pilot (same page, Polarization).
- Tracked passages carry the ship flown: the poller reads ESI `GET /characters/{id}/location` and `GET /characters/{id}/ship` (scopes `esi-location.read_location.v1` and `esi-location.read_ship_type.v1`, already asked for when linking) in the same tick and applies the ship before the jump, so `character.jumped.shipTypeId` is the hull that jumped. They count cold (hull mass); whoever knows the prop module ran sets them hot.
- Passages (migration `mapping/0200_passage_log`, WP3's range 0200-0299): `source` `tracked` or `manual`, `mass_mode` `cold` / `hot` / `custom`, `higgs`, `entangler`, `note`, `created_by`; `character_id` and `event_id` became nullable (a jump logged by hand has neither), so the table is rebuilt with its rows copied. Members log jumps by hand (ship by name, direction, cold/hot/custom, Higgs Anchor and entangler where they fit, up to 20 at once, a note), change how any passage counts and delete mistakes; events `connection.passage` (now also for manual ones, `characterId` null), `connection.passage_updated` and `connection.passage_removed`, audited (`passage` entity, on the connection's history). "Reset counter" stamps `massStatusAt` like setting the mass status again: earlier passages stay in the log, marked as not counted.
- The mass estimate is a range (`ConnectionIntelDto.mass.range`): the status band (fresh 50-100 %, reduced 10-50 %, critical 0-10 %) of a total between 90 % and 110 % of the type's, minus the mass counted since `massStatusAt`; each counted passage with an unknown ship lowers the minimum by the max jump mass. `overdrawn` when more passed than the band allowed (the status was set late or jumps are missing). `remaining` keeps its meaning (nominal upper bound) for urgency and the panel. Holes whose regeneration is at least their total (frigate holes) never run down and cannot be rolled.
- Rolling plans (`planRoll`, mapping domain, pure): the crew's ships each with a cold and a hot mass (Higgs Anchor always on, the entangler on going out and off coming back hot); round trips out cold and back hot, out only while the mass on the hole plus that jump stays below the least the hole may have left (so it cannot strand the ship), fillers first and then the trip with the heaviest jump back, so the first jump that may close the hole is a jump home. When no safe jump out is left and the hole may still be open, the trip with the least mass out per mass back goes, and the plan says that jump may strand the ship (`risky`/`strand`); a trip never leaves less on the hole than the lightest jump out (only a stranding jump could close it then) unless it closes it, trips coming back cold where that helps. `ok` only when the plan closes the hole whatever its real mass with nobody at risk; polarization is flagged when a pilot jumps the same way in consecutive trips, and ships of one kind take turns to avoid it. `POST /api/maps/:mapId/connections/:connectionId/roll-plan` (viewer) answers with the crew's masses and each step's possible remaining mass and statuses; the dialog adds the fork's "jumps until half / critical / collapse" table.
- Merged maps and passages: passages stay with the source map that recorded them. A merged connection shows the passages of every visible source holding it that shares `connectionStatus` (pilots only with `characters`), read through `ChainSource.passages`; a tracked jump two sources recorded counts once (an opaque FNV-1a key of pilot, systems and moment, so the pilot is not readable without the scope). Logging on a merged map writes through one source only, the one that takes new objects among the writable sources holding the hole (ChainCommand `passages.log`); "Reset counter" writes to every such source (`passages.reset`). Passages from shares are read-only on the merged map (changed where they were recorded); a standard map's own passages stay editable in its merged view. Merged maps refetch passages every 30 s while a connection is open: source passage events are not republished on merged streams.
- Lifetime is decided in one domain function, `connectionLifetime` (mapping): the wormhole type's lifetime when the type is known, else the default by class as the Wanderer fork assigns it to new holes (`get_time_status` in `map_server_connections_impl.ex`: frigate holes 4.5 h, a hole touching C1-C4 16 h, C5/C6 24 h, anything else 24 h), counted from when the map first saw the hole, and at most 4 h after it was marked EOL. The intel, the sidebar and the sweeper all read it; Wanderer's lifetime stages (arriving with the importer) will switch over inside it.
- The sweeper (`ChainSweeper`, every 5 minutes like the fork's connection cleanup, not in tests or maintenance, audited as the `sweeper` process): a wormhole turns EOL when the last 4 h of its lifetime begin (`eolAt` set to that moment, so Discord and webhooks report it like any EOL); one past the latest moment it can exist is deleted as a deliberate removal (tombstone) `expiredConnectionMinutes` later (default 0: the fork deletes 4 h after the EOL mark with its default `WANDERER_MAP_CONNECTION_AUTO_EXPIRE_HOURS` 24, `..._AUTO_EOL_HOURS` 21 and `..._EOL_EXPIRE_TIMEOUT_MINS` 60, the end of the EOL window too); a visible system with no connection, no tracked character in it (online or not), not locked and not home, untouched (system or signatures) for `staleSystemMinutes` (default 15, the fork's `@system_auto_expire_minutes`) is hidden, keeping its intel. Deviations from the fork: locked connections (`locked`, arriving with the importer; `connectionLocked`) and home systems are never swept, while the fork sweeps locked ("save mass") connections; stargates and bridges are never swept. Instance settings `expiredConnectionMinutes` (null never), `autoEol`, `staleSystemMinutes` (null never), in Admin, Instance, Chain cleanup.
- Auto-dangerous jumpgates: the fork never marks connections dangerous by itself (only by hand, import or the bridge import's separate table), so neither does Darkbeacon.
- The connection sidebar: a click on a connection selects it alone and opens it in the map's one sidebar shell (`SidebarShell`, shared with the system sidebar: same width, resize and phone sheet): header with both ends (each selects its system) and the states in words (mass, time, mass saved, dangerous, bubbled as badges in the panel, never on the edge), then Connection, Mass and Passages sections. The edge's only text stays the size letter; the hover card adds "N jumps counted, X t". The connection's context menu gains "Log a jump…" (members) and "Plan a roll…" (built in `map/menus/passages.tsx`).
- Telemetry: `passage_logged` `{ source: tracked|manual, mode: cold|hot|custom }` from `connection.passage` events (demo seeding counts nothing) and `roll_planned` `{ result: ok|risky|impossible }` from the roll-plan route; enums only.
- The demo chain logs a rolling crew's jumps by hand: a Megathron cold out and hot back and an Orca cold out and hot back with a Higgs Anchor through the high-sec static, and two Megathron jumps on the low-sec static from before it was marked reduced (shown, not counted).
- Pasted fits (EFT, as the game copies a fit) are weighed on the server (`POST /api/universe/ships/fit-mass`, `fitMass` in mapping's domain): hull, plus every always-on `massAddition` (armour plates) and the subsystems' own mass (`wormholes.json` `fitItems`, published types only, by name), scaled by the rigs' `massBonusPercentage` (Higgs Anchor); hot adds the largest prop module, as only one runs; offline modules, cargo and drones (`x3` lines) do not count. Like the fork (`fits.ex`), but the mass entangler is left out of a fit's weight: it is an active module, switched on for the jump out only. "Log a jump" logs a fit's cold or hot weight as a custom mass (named in the note); a rolling crew member may be a pasted fit (`RollShipRequest.fit`). Reading the flown fit from ESI assets (the fork's opt-in `esi-assets.read_assets.v1`) is not built.
- Block precedence was corrected to Wanderer's (it used to let any grant beat a corporation or alliance block, so a blocked spy corporation inside a member alliance got in). The Wanderer importer (`feat/import-wanderer`, `importing/src/domain/acl.ts` `planAccess`) must follow it when it lands: a subject blocked in any ACL becomes one `blocked` rule whatever its kind (not only characters), and a corporation or alliance block is reported as mapped 1:1, no longer as an approximation.
- Access rules can change their role in place (`PATCH /api/maps/:mapId/access-rules/:ruleId`, event `access.rule_changed` with the old rule as `before`). Map managers list rules and, as in Wanderer, add, change and remove viewer, member and blocked rules (`MANAGER_ASSIGNABLE_ROLES`), never admin or manager rules nor anything that makes one; admins manage everything.
- Wanderer's reusable access lists become "copy rules from map" (`POST /api/maps/:mapId/access-rules/copy`, admin here, manager or more on the source): rules stay per map, subjects the map already has keep their role unless `overwrite`. The same merge imports the rules of an exported map and of a duplicate.
- Map lifecycle (migration `mapping/0400_map_lifecycle`): maps have a `description` (500 characters, on the maps page) and `deleted_at`. `DELETE /api/maps/:mapId` now deletes softly: `map.trashed` on the map stream, the map has no owner for access (`MappingMapOwnership.ownerOf` is null) so nobody holds a role, open sockets are re-checked and dropped, the address stays reserved, rules, shares and webhooks stay, and maps that merge it read it as empty. Instance admins see every map in `GET /api/admin/maps` (name, owner, visible systems, rule count, deleted) without any content access, delete (`POST …/trash`), restore (`map.restored`) and purge (`DELETE /api/admin/maps/:mapId`, only deleted maps; `map.removed` as before, which the other modules follow).
- Map owner handover: `PUT /api/maps/:mapId/owner` by the owner, `PUT /api/admin/maps/:mapId/owner` by an instance admin (deleted maps too); the account must exist. Recorded as `access.owner_changed` (so realtime re-checks) plus `map.settings_changed` with the new owner.
- Locking and unlocking a system needs manager, as Wanderer's `lock_system` (our fork, v1.103.4; upstream later let members lock); on composites as well.
- "Only admins create maps" is the instance setting `mapCreation` (`everyone` by default), read by mapping through the `MapDirectory` port (composed from identity and access in `adapters/mapping/map-directory.ts`) and shown to the web in `InstanceInfoDto.mapCreation`.
- A new map may come with a starter rule (`CreateMapRequest.starterRule`: one of the creator's corporations or alliances as member or viewer), as Wanderer's "create default access list"; it is checked before the map is created, so a refused rule creates nothing.
- Darkbeacon map files are `darkbeacon.map` v1 (`MapExportDocument` in `dto/map-export.ts`): map name, slug, description, kind, settings and labels, every system (hidden ones with their intel), connection and signature without `mapId` or provenance, and the access rules when an admin asks (`?accessRules=true`). Export is for managers (`GET /api/maps/:mapId/export`, a download); `POST /api/maps/import` makes a new map owned by the caller with new ids (signatures keep their link through the file's connection ids), leaves out systems the universe does not know with what hangs on them, and refuses another format or version. Bodies up to 32 MB as `application/vnd.darkbeacon.map+json` (JSON bodies stay at Fastify's 1 MB). Round trip is tested: export, import, export again gives the same chain.
- Duplicate (`POST /api/maps/:mapId/duplicate`, map admins) is an export and import in one call, signatures optional; rules come along through access. Settings files are `darkbeacon.map-settings` v1 (settings and labels): export for managers, import for admins (labels optional).
- Batches (`POST /api/maps/:mapId/batch` and `…/batch/delete`, members): one transaction through the single use cases, so a refused change (a locked system, an unknown system) rolls the whole batch back and every change is audited and published as usual. Systems are added or restored then given the fields; connections are found by their two systems in either direction, else added. Maps that merge others refuse batches (409); their single routes write through as before.
- Connections by their systems: `GET|PATCH|DELETE /api/maps/:mapId/connections/between/:source/:target` (either direction), found in the map's snapshot so merged maps answer with the merged connection.
- `GET /api/maps/:mapId/events?sinceSeq=&limit=&types=` pages the durable log (what the WebSocket and webhooks carry), with `nextSeq`, `headSeq`, `more` and `gap` (pruned events: read the snapshot again). Wanderer's `?since=<time>` ring is not answered.
- Server-Sent Events are a transport of the realtime hub (`SseStreams`): `GET /api/streams/:stream/sse` subscribes like a WebSocket (same check, replay from the log, re-checks after access changes, a revoked key or ended session ends the stream), resumes after `sinceSeq` or `Last-Event-ID`, otherwise starts at the newest event (`snapshot=true` sends one first), filters by `types`, writes `id: <seq>` frames and a `: keepalive` comment every 25 s. At most 20 streams per client address and 10 per account or key (429 before the stream starts); streams close after a restore.
- The Wanderer-compatible API (`apps/server/src/modules/wanderer-compat`, routes `wandererCompat`) is a driving adapter over Darkbeacon's own reads: the realtime check and snapshot (so map roles, key caps, merged maps and hidden systems behave as everywhere), identity for corporations, alliances and tickers. Shapes follow Wanderer v1.103's code, not its blog posts (`{"data":{"systems","connections"}}`, 17 system keys, 12 connection keys, status integers of its map UI: 0 clear, 1 home, 2 friendly, 4 warning, 5 target, 6 hostile; Darkbeacon's empty is 0 and occupied 4). Errors are Wanderer's `{"error": …}` bodies and statuses, including its 400 for an unknown `map_id`. Map systems and characters get stable name-based UUIDs.
- Wanderer's map key is a Darkbeacon API key (`map:<id>:*:read`), authenticated by the api-keys bearer machinery like every key; the routes ask the guard for nothing (`scope: 'none'`) because `:mapId` may be a slug there, and the controller checks the key's scope for the resource on the resolved map. Old Wanderer key values are not imported: bots change the base URL anyway, and a key made here can be revoked and scoped.
- Wanderer's SSE stream runs on `SseStreams` like the native one. Event ids are the ULIDs of Darkbeacon's UUID v7 event ids (the same 128 bits, so they sort the same); `last_event_id` replays the log's last 1000 events after it. Removals that Darkbeacon names by id (connections, signatures, characters) are described from what the stream saw (its snapshot and earlier events).
- Webhooks count deliveries that failed for good in a row (every retry used up; tests and deliveries of a disabled webhook do not count) and turn themselves off at ten, as Wanderer does, with `disabledReason` and the audit event `webhook.auto_disabled` (migration `notifications/0002_webhook_health`); a delivered one resets the count, turning it on again clears both. `POST …/webhooks/:webhookId/rotate-secret` gives a new secret once (`webhook.secret_rotated`).
- Instance switches (Admin): `webhooksEnabled` (off: nothing is queued or retried; events meanwhile are not delivered later) and `apiAccess` (off: `ActorResolverRegistry.verifyBearer` refuses every bearer token with 403, so keys and OAuth tokens stop on HTTP, WebSocket, SSE and MCP alike; such refusals are not counted as failed tokens). Browser sessions are unaffected.
- Every client address has 600 requests a minute (`RATE_LIMIT_PER_ADDRESS`, 0 turns it off), signed in or not, on top of the per-key limits; loopback (the server's own page renderer) is not counted. Over it: 429 with `retry-after`.
- Accounts can be disabled by instance admins (`PUT /api/admin/accounts/:accountId/disabled`, never the owner or oneself; migration `identity/0005_account_status_and_invites`): sessions are deleted and no longer resolve, sign-in is refused, API keys and OAuth approvals stop authenticating, and the access module gives a disabled account no map role at all (`AccessSubjects.disabled`), not even on maps it owns, so tracking stops too. Recorded as `account.disabled_changed`; enabling restores everything.
- Instance admins list every linked character with its account (`GET /api/admin/characters`) and unlink one (`DELETE …/:characterId`): the same `character.unlinked` and `access.account_changed` events as unlinking one's own, with the admin as actor; the owner can link it again.
- Sign-up policy (instance setting `signIn`, Wanderer's invites and registration restriction): `open` (default) or `restricted`, where a sign-in that would create a new account is allowed only for a character in an allowed corporation or alliance (EVE sign-in), a member of an allowed Discord server (asked with the user's token at Discord sign-in), or someone holding an invite. Existing accounts always sign in (disable them instead); the first account (the owner) is always created; demo logins are not restricted. Invites (`SignUpGate` in identity, table `invite`) have a note, an expiry and a number of uses, keep only the token's hash, are shown once as `PUBLIC_URL/login?invite=<token>`, are carried through the OAuth round trip in the sealed pending state, and are used up atomically in the account's transaction (`invite.created|revoked|used` on the audit stream).
- The map characters page (Wanderer's, managers): `GET /api/maps/:mapId/tracking/characters` lists every character tracked on the map with its account and since when; `DELETE …/:characterId` takes anyone's character off the map (`character.untracked` with the manager as actor); its owner may track it again.
- Offline characters for managers only (map setting `offlineForManagersOnly`, Wanderer's `restrict_offline_showing`) is enforced on the server: the characters list, the snapshot part and live events are cut for viewers and members by `OfflineVisibility`. Realtime gained per-follower event filters (`RealtimeRegistry.registerEventFilter`, applied by the hub, the SSE stream and the events page with the follower's current actor): for them a character going offline becomes `character.untracked`, coming online `character.tracked` with its presence, and moves of offline characters are dropped. The option and roles are cached briefly and forgotten on `map.settings_changed` and access changes.
- "Only tracked characters" (map setting `onlyTrackedCharacters`, Wanderer's option) is a gate in the web app, as in Wanderer's LiveView: the map asks the person to track all their characters before it opens. The API and keys are not gated.
- With offline characters for managers only, everyone still sees their own characters (the list, snapshot and events are filtered per follower by account). The "only tracked characters" gate lets map admins through, so whoever set the option can always open the map and change it; viewers, who cannot track, stay out as in Wanderer.
- Admin UI for WP7 lives in its own files: `screens/AdminMaps.tsx` (Maps tab), `AdminCharacters.tsx` (People), `AdminAccess.tsx` (sign-up, map creation, API and webhook switches); the map settings dialog has `MapAccess.tsx` (Access, now also for managers), `MapCharacters.tsx` (Characters, managers) and `MapTransfer.tsx` (Copy and hand over: map file, settings file, duplicate, owner).
